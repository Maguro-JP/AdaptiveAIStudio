## 私が外したところ

- **乱数の重みで「通った」と報告してきた。**本物の重みは一度も読んでいない。
  配った先で毎回そこで壊れ、そのたびに利用者が記録を送る側に回った。
  → 本物の重みを読める場所（CI のランナー）で、答えの中身まで見る道を先に作る。
- **「テストが緑」を「使える」として報告した。**
  → 報告に「確かめていないこと」を同じ長さで並べる（`scripts/not-checked.mjs` の出力を
  そのまま写す）。一度貼ったら、中身が変わるまで貼り直さない。
- **同じ穴に二度落ちた。**行末（CRLF）で Windows だけ落ちる試験を、一度目は読む側で
  そろえて直し、二度目も読む側で `\n` を直に書いた。
  → 原因の側（`.gitattributes`）で消し、git に聞いて確かめる試験を置いた。
- **片方にだけ足した。**パネルの種類を画面側（`TITLES`）にだけ足し、配置を受け取る側
  （`PANEL_KINDS`）に足さなかった。試験は通り、画面を開いたら中身の無い札が出た。
  → 二箇所に分かれているものは、一致することを試験で留める（`test/panel-kinds.test.ts`）。
- **確かめずに書いた注釈が、前提として残った。**「戻せる形（`setRangeText`）」と
  コードに書き、一つずつの置換をそれで書いた。Chromium で押してみると**戻らない**
  （丸ごと代入も同じ。人が打ったのと同じ扱いで入る `execCommand('insertText')` だけが
  戻し履歴に乗る）。**直したつもりの所が、直っていないまま「直した」と書いてあった。**
  → ブラウザの中で決まることは、ブラウザで押して測ってから書く。測った結果は
  `scripts/sweep.mjs` に置いて、次に崩れたら落ちるようにする。
- **走らせる機械で結果が変わる確かめを、また作った。**乱数の模型は終わりの合図を出さず、
  遅い機械では吐き切るまで何分もかかる。308 秒で通った次の回は 600 秒でも終わらなかった。
  → 出す量の側を決める（`maxTokens` 32）。待つ上限を伸ばさない。

## 手順の要点

```
npm test              # テストだけ（型は見ない）
npm run typecheck     # 型
npm run check         # 両方 + 画面 + 本物の数え方 + 「確かめていないこと」の一覧
npm run check:bundle  # 配る形に組んで、その中でもう一度（linux で 10 分ほど）
npm run bundle        # 手元で bundle を作る（--node-here で今の Node ごと）
npm run shot          # README の画面の例を撮り直す（画面を変えたら）
```

- CI は PR・手で頼んだとき・週に一度だけ。**`bundle`（Windows で配る形を通す）は
  PR では回らない。**手で回すときは、先に断る。1 回 10 分ほど、Windows は 2 倍で数える
- 版を上げるときは `package.json` を直して同じコミットに入れ、`main` へ push。
  そのあと `git push origin main:release/vX.Y.Z` で release が組まれる
- 作業の枝を PR にして squash で main へ。マージ済みの枝に積まない（main から切り直す）
