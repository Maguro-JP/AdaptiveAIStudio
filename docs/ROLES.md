# 人員 — この世界に誰を住まわせるか

## 0. 肩書きではなく気質

役職を「担当分野」で分けるだけでは足りない。効くのは気質の方。

同じコードを、同じツールで、同じモデルに見せても、
どういう態度で臨むかで見つかるものが変わる。

実際に走らせた結果:

```
対象: input.split(',') で分解して parts[1].trim() を呼ぶ関数

合議: 検査担当 / 破壊担当 / 安全担当
    検査担当: 問題なし
  💡 [破壊担当] カンマの無い入力で parts[1] が undefined になり trim で落ちる
  💡 [安全担当] 外部入力を検査せずに分解している
```

真面目な検査担当は正しく「問題なし」と答えている。 手順どおりに確かめれば動くから。
それは怠慢ではなく、その役割を正しく果たした結果。

だから、意地の悪い人を別に配属する必要がある。

## 1. 配属されている人員

| 呼び名 | 役職 | 気質 | 権限 |
|---|---|---|---|
| SMITH | 作業担当 | 推測で書かない。担当範囲の外に手を出さない | 読/書/実行 |
| WARDEN | 検査担当 | 几帳面。「たぶん動く」で終わらせず実際に走らせる | 読/実行 |
| GREMLIN | 破壊担当 | 意地が悪い。正常系に興味がない。壊れ方に興味がある | 読/実行 |
| SENTINEL | 安全担当 | 性悪説。「する人はいない」ではなく「できてしまうか」 | 読 |
| CURATOR | レビュー担当 | 半年後の自分が読むつもりで見る。好みは指摘しない | 読 |
| ARCHITECT | 計画担当 | 曖昧なまま進めない。完了条件を先に決める | 読 |
| HERALD | 報告担当 | 結論から書く。うまくいかなかったことを隠さない | 読 |
| SCOUT | 調査担当 | 思い込みで答えない。手元を調べ尽くす | 読/実行 |
| ENVOY | 情報担当 | 外へ出る。出典の無い話を持ち帰らない | 読/外 |
| QUARTERMASTER | 整備担当 | 道具そのものを良いものへ保つ。利用者の仕事には立ち入らない | 読 |
| ARCHIVIST | 整理担当 | 溜めることより引き出せること。重複を許さない | 読/書 |

### 呼び名で呼ぶ

肩書きで呼ぶと機能に見えるが、名前で呼ぶと人に見える。
社会として動かすなら、後者の方が正しい。

`SCOUT` は手元を調べ、`ENVOY` は外へ出る。
同じ「情報担当」でも、行く先が違えば別の人。

`ENVOY` と `QUARTERMASTER` も分けてある。
あちらは利用者の仕事の話、こちらは道具の側の話。
新しいモデルが出たという知らせを ENVOY に持たせると、
利用者にとって必要な報告が道具の都合に押し出される。
見る先が違えば、判断の基準も違う。

| | 何を見るか | 何で選ぶか |
|---|---|---|
| ENVOY | 利用者の仕事に関する外の情報 | この場所に関係あるか |
| QUARTERMASTER | 使っているモデル・実行基盤 | いまより良いか、そしてこの機械で動くか |

思考モードも `BRIEFING`（外部情報）と `UPKEEP`（整備）で分けてある。

### 気質は行動に落とす

「丁寧に見てください」では何も変わらない。気質は具体的な手順にする。

破壊担当の場合:

```
- 境界を攻める: 0件、1件、極端に大きい値、空文字、null、未定義
- 順序を崩す: 初期化前に呼ぶ、二重に呼ぶ、途中で中断する
- 型を裏切る: 数値のつもりの場所に文字列
- 同時に起こす: 同じ資源へ並行にアクセスする
- 失敗させる: ファイルが無い、権限が無い、応答が返らない
- 「起きるかもしれない」ではなく「このコードではこうなる」と書く
```

最後の一行が重要。気質だけ与えると、根拠のない不安を並べ始める。

## 2. 権限は渡さないことで守る

| 権限を持つ役職 | それ以外 |
|---|---|
| 書き込み: 作業担当・整理担当のみ | 調べて報告する |
| 実行: 検査・破壊・調査・作業 | 読むだけ |

破壊担当に書き込みを渡さないのは、信用していないからではない。
役割上必要ないから。必要のない権限は事故の原因にしかならない。

「変更しないでください」とプロンプトに書くのではなく、
ツールを配らない。[ハーネス設計](HARNESS.md)と同じ考え方。

## 3. 合議

気質の違う担当を、同じ対象に同時に当てる。

```
/panel src/parse.mjs を見てください
```

- 全員の合意は取らない。気質が違う以上、見解が割れるのは正常
- 一人が失敗しても他は続く
- 同じ指摘が複数から出たら1つにまとめ、誰が同意したかを添える
- 見つかったものは提案として溜まる。実行するかは利用者が決める

ローカルは計算が無料なので、人数を増やす代償がほとんど無い。
クラウドでは人数分だけ課金されるため、これは局所的な優位になる。

## 4. 人員を追加する

コードを触らず、設定から配属できる。
「こういう気質の担当がいたら拾えるはず」と思いついたら足す。

```jsonc
{ "roles": [
  {
    "id": "perf",
    "name": "性能担当",
    "responsibility": "遅いところを探す",
    "disposition": "体感より計測を信じる。推測で最適化しない。",
    "access": ["read", "execute"],
    "instructions": ["まず計測する", "一番遅いところから見る", "効果を数字で示す"]
  }
] }
```

既存の役職を土台に、気質だけ変えることもできる。

```jsonc
{ "roles": [
  { "id": "gentle-breaker", "extends": "breaker",
    "name": "穏当な破壊担当",
    "disposition": "意地悪だが、現実に起こりうる範囲に留める。" }
] }
```

合議の参加者も設定で決める。

```jsonc
{ "panel": { "roles": ["tester", "breaker", "security", "perf"], "parallel": 3 } }
```

項目が足りない役職は登録しない。 中途半端な役職は、いない方がまし。

## 5. これから配属したい人員

思いついた時点で足していく。以下は候補。

| 役職 | 気質 | 何を拾うか |
|---|---|---|
| 性能担当 | 体感より計測を信じる | 遅い箇所、無駄な再計算 |
| 移植担当 | 「うちの環境では動く」を信じない | OS差、パス区切り、文字コード |
| 保守担当 | 半年後に人が辞めた前提で見る | 属人性、暗黙の前提 |
| 利用者担当 | 作った人の意図を知らないふりをする | 使い方が分からない、エラー文が不親切 |
| 記録担当 (CHRONICLER) | 決めたことを覚えている | 過去の判断との矛盾 |
| 反対担当 (DEVIL) | 全ての提案に一度は反対する | 合意の早すぎる形成 |

最後の「反対担当」は、合議が全員一致で流れるのを防ぐためのもの。
人の会議でも、賛成しかいない会議は危ない。

## 6. 原則

1. 肩書きではなく気質を定義する。何をするかより、どう臨むか
2. 気質は具体的な手順に落とす。抽象語だけでは行動が変わらない
3. 権限は渡さないことで守る。禁じるのではなく配らない
4. 見解が割れることを許す。全員一致を目指さない
5. 足りない役職は足せるようにする。思想は後から増える

## 7. 名簿の寿命 — 消さない、変えたら周知する

役職は都度最適化する。仕事に対して合わなくなったら、担当を切り分けたり、
より適した仕事を与えたりする。ただし消しはしない。

| やること | やらないこと |
|---|---|
| 仕事を細分化して、一部を新しい役職に渡す | 役職ごと削除する |
| より適した仕事に付け替える | 名前を毎回付け直す |
| 違和感が出たときだけ改名する | 気分で用語を揺らす |

名前と機能が変わりすぎると、呼ぶ側が混乱する。だから基本は変えない。
変えるのは「違和感が出たとき」だけ。

### 引き継ぎ

役職の仕事が他に移ったときは、`retired: true` と `succeededBy: [...]` を立てる。
名簿からは消えない。古い ID で呼べば `RoleRegistry.get()` が後任に繋ぐ。
改名した場合は `formerly: [...]` に旧称を残す。こちらも古い名前で届く。

- `roles.active()` — 今、仕事が割り当たる人
- `roles.roster()` — かつて居た人も含めた全員

### 周知

`RoleLedger` が起動ごとに名簿の署名を取り、前回との差分を出す。

| 種別 | 意味 |
|---|---|
| `joined` | 配属 |
| `renamed` | 改名 |
| `reassigned` | 担当変更 |
| `retuned` | 姿勢の調整 |
| `authorized` | 権限変更 |
| `succeeded` | 引き継ぎ |

差分は起動時に一度だけ表示され、`.aas/roles-ledger.json` に「周知済み」として記録される。
表示前に落ちても未周知のまま残るので、次の起動で必ず伝わる。

役職が名簿から消えていた場合、それは変更ではなく方針違反として報告される。
引き継ぎ先を `succeededBy` で示すこと。居なくなるのは、なしだ。

## 8. 外への出口

権限は `read` / `write` / `execute` に `network` を加えた4つ。
禁じているのではなく、配っていない。持たない役職はツールが無いので、外に出ようがない。

### 一度「出口は一人だけ」にして、やめた

以前は `network` を持つのを ENVOY ただ一人にしていた。
出入りが見えるように、という理由だった。

これはやめた。 外の情報が要る役が増えるたびに ENVOY を経由させることになり、
agent を一段挟むぶん遅く、途中で情報も落ちる。
制限のために性能を落とすなら、その制限に意味は無い。

守るべきものは「出口の数」ではなかった。

### 守るのは、外と書き込みを同じ手に持たせないこと

外から取ってきた内容には、こちらを操ろうとするものが混ざり得る。
危ないのは、それを読んだ役がそのまま書けるとき。指示が直接ファイルに届く。

だから条件はこれ一つにした。

> network と write を同じ役職に持たせない。

ENVOY も QUARTERMASTER も `write` を持たない。
外を見て、報告するところまでが仕事で、直すのは別の役の仕事になる。
この一線さえ守れば、外へ出られる役職が何人いても構わない。

### 守っている三つ

1. 行き先を決め打ちにする — 許可リストのホストのみ、https のみ、転送は追わない
2. 取ってくるだけ — GET のみ。資格情報は一切送らない。承認は書き込みと同じ重さで求める
3. 外れても止まらない — 繋がらなければ「行けなかった」と返し、手元で分かる範囲の結論を出す

3 が要点。外が落ちたことで手元が止まるなら、それは外部に依存しているのと変わらない。

### 既定の行き先

| ホスト | 何のため |
|---|---|
| `registry.npmjs.org` | 依存の実際の最新版 |
| `api.github.com` | リリース、既知の不具合 |
| `raw.githubusercontent.com` | 変更履歴そのもの |
| `nodejs.org` | 実行環境の版と保守期限 |
| `api.osv.dev` | 既知の脆弱性 |

検索エンジンやニュースサイトは入れない。雑音を持ち帰らせないため。
足りなければ `network.allowedHosts` で足す。`network.enabled: false` で完全に閉じられる。

### 朝いちで、外を見て回る

MORNING BRIEF（毎日7時）が ENVOY を起こす。
このとき渡すのは「何か新しい話は無いか」ではなく、手元で数えた事実。

```
# 手元で数えた事実
実行環境: node 22.22.0
要求している環境: node >=22

依存 2 件（宣言 / 実際に入っている版）:
  left-pad    ^1.3.0 / 未導入
  typescript  ^5.6.0 / 5.6.3  (開発用)

# 訊きに行くなら
この一覧のうち、気になるものを一つだけ選んで確かめてください。
  最新版  https://registry.npmjs.org/<名前>/latest
全部を調べようとしないこと。
```

漠然と外へ出すと雑音しか持ち帰らない。
「この依存のどれが古いか」なら、答えは一つに定まる。

持ち帰ったことは記憶に `fact` として残る。同じことを何度も訊きに行かないため。

### 考えている間も、読むことは止めない

暇なときの思考には、承認を必ず断る作業者を渡している。
ただし断るのは書き込みとコマンドで、外を読むことは通す。

手を出すことと、調べることは違う。
読むだけならこの場所は変わらないし、
そこを止めると ENVOY は日課の中で何もできない。

### 手元が先

BRIEFING（外部情報の時間）は、まず手元を読む。
入っている依存の実際の版、変更履歴、型定義 —— 手元に答えがあることを外に訊きに行かない。
外に出るのは、手元をいくら読んでも分からない一点だけ。
