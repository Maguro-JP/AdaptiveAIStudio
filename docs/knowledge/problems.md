## 2026-09-30 遠くの MCP で、止めた問いの流れが残り、相手の問いを返事と取り違え、版を名乗っていなかった
- 原因: 問いごとの繋ぎを切る口が無く、流れ（SSE）の読み手は次の塊まで待ち続けた。読み口は番号だけを見て、相手からの問い（ping 等）を
  こちらの返事として受け取った。名乗りの後の問いに `MCP-Protocol-Version` を付けていなかった（#134〜#136）
- 解決: 問いごとに AbortController を持ち、止めた・時間切れ・stop()・#fail で切る。`method` を持ち `result`・`error` を持たないものは問いとして
  答える（ping は空、ほかは -32601）。取り決めた版を見出しに付ける（見出しに使えない形なら付けない）
- 再発防止: 相手役をその場で書く試験（黙る SSE・同じ番号の ping・版を記録する相手・改行入りの版）。直す前の版と、守りを外した版で落ちることを見た
- 失敗した手: 試験で 200ms・800ms の決め打ちの待ちを書いた。読み直しで「相手が受け取ったのを見てから止める」形に直した
- 残り: 相手がこちらの知らない版を返しても切らない（切ると、版だけ新しく中身は読める相手まで繋がらなくなる）

## 2026-09-30 止めた外の相手（MCP）に、止めたことが伝わらず、止まらずに残った
- 原因: ■ で MCP の呼び出しを止めても、こちらが待つのをやめるだけで相手に知らせていなかった。止める道は SIGTERM だけで、無視する相手は
  手を放した後も生き続けた。相手が入力を閉じた後に書くと EPIPE を受ける聞き手が無く、こちらのプロセスごと落ちる道もあった（#129・#130）
- 解決: 止めたら `notifications/cancelled` を送り、待ちをその場で片づける（知らせは届かなくても失敗にしない）。EPIPE を受けたら相手を止め、
  以後は待たずに断る。止めるときは SIGTERM から 3 秒で SIGKILL
- 再発防止: 相手役をその場で書く試験（取り消しの id が届く・500 で断られても巻き込まない・入力を閉じても落ちない・SIGTERM を無視しても
  残らない）。どれも直す前の版で落ちることを見た。時間に頼らない順（閉じてから返す）にし、途中で落ちても相手を残さない
- 失敗した手: 最初の試験は相手が返してから入力を閉じ、300ms 待って書いていた。負荷で順が入れ替わると落ちるので、閉じてから返す順に直した
  （押す前の読み直しで見つかった）
- 残り: 遠くの相手で、止めた呼び出しの返事の流れが開いたまま残ることがある。npx のように孫を立ち上げる相手の孫が残りうる
- 揺れた試験: `test/input.test.ts` の Ctrl-C の試験が 40 回に 1 回ほど落ちた。READY と「> 」が別の塊で届くと、試験が SIGINT を
  二度送って二度押しになっていた（製品ではなく試験の送り方）。一度だけ送る形にし、子の終わりは出力を読み切った後の 'close' で待つ。
  直した後は 80 回で 0 回。最初は 'exit' と 'close' の取り違えと見立てたが、替えても 80 回に 3 回落ちたので外れていた

## 2026-09-29 待ちに上限が無い・■ が届かない所で、依頼が止まったまま戻らなかった
- 原因: 相手の `Retry-After` をそのまま待つ（数時間もあり得る）、子プロセス（nvidia-smi・git）に時間切れが無い、run_command の標準入力を
  開いたまま、裏の問い合わせに誰も止めない signal を渡す、MCP の呼び出しに ■ を渡さない、CLI の Ctrl-C を rl の SIGINT だけで受ける
  （`terminal: false` なので来ない）、の形が散らばっていた（#125・#127）
- 解決: 待ちには上限を付け、上限は「次の候補があるか」「遅い回線でも終わるか」で決める。■ は待っている所まで signal で届け、止めた結果の
  空を「無かった」「割れなかった」と読まない。Ctrl-C はプロセスの SIGINT で受け、二度押しで終わる
- 再発防止: 待つ所ごとに、返らない相手（眠り続ける node・本文を止める http・返事をしない MCP）を作って、上限か ■ で抜けることを試験で見る
  （`test/orchestrator.test.ts`・`machine-probe`・`git-timeout`・`provider-error-body`・`mcp-bytes`・`input`）
- 失敗した手: 最初は候補が一つでも 30 秒を超える待ちを落としていた（待てば通る 429 を落とす）。配布元への問い合わせを 15 秒で打ち切り、
  打ち切った空を「無かった」と書いていた。どちらも押す前の読み直しで見つかった
- 残り: 端末の Ctrl-C は同じプロセスグループの子にも届く（確かめた）。inproc-host は止まらないようにしたが、llama-server は止まる。
  MCP は止めても相手へ取り消しを送らない（2026-09-30 に送るようにした）

## 2026-09-29 読めない・見られない・書けないを「無い」「空」「済んだ」と取り違え、消す・書き直す・状態を進めていた
- 原因: `readFile(...).catch(() => undefined)` のような一行で、読めない失敗（EACCES・EBUSY・EISDIR）を「無い」と同じに扱っていた。
  そこから消す（`.env` のトークン・戻すファイル）、空で書き直す、済んだ・諦めたことにする、に進んでいた（#108〜#117、#118〜#122）。
  書きの側も同じで、戻し終えた戻り先を消せないのを黙って捨て、一覧に残った戻り先をもう一度押すと新しい直しを古い姿で上書きしていた
- 解決: 「無い」（ENOENT・ENOTDIR）だけを空にし、ほかは投げるか「分からない」に回す（`src/harness/put-back.ts` の `isAbsent`・`readPrior`）。
  書けなかったことは返して、画面が言う（`src/core/undo.ts` の `restoreWarnings`）
- 再発防止: `test/lenient-reads.test.ts`（読みの側）と `test/swallowed-writes.test.ts`（書きの側）が、失敗を空で受ける一行の形をファイルごとに
  数え、理由を書いた一覧に無いもの・一覧より増えたもの・減ったのに一覧が古いものを落とす
- 失敗した手: 最初の正規表現は `[] as string[]` の形も、`.then(() => true, () => false)` の形も数えておらず、押す前の読み直しで見つかった。
  直しの側でも、git が落ちたときに投げずに「比べられない」を返す道を拾っておらず、読み直しで見つかった
- 残り: 数えるのは一行に収まる形だけで、`try { … } catch { }` や、書き込みを包んだ関数（`saveJournal(…).catch`）は見ていない

## 2026-09-24 きれいだったファイルの「前」を索引から引いていた。`git add` の後では後の中身になる
- 原因: 索引は `run_command` の `git rm` / `git add` / `git mv` で動くのに、触った後の索引を「前」と読んだ。取れないものを「前は無い」と読み、戻すときに在ったファイルを消す道もあった。`--show-toplevel` + `relative()` は、シンボリックリンク越しの作業場で `../../` の道を作った
- 解決: HEAD から引く（`headContent`。absent / content / unavailable を分ける）。道は `--show-prefix`。名前変更の元も記録する。上限は一つ 8MiB・合計 64MiB。覚えている「前」は回の終わりに書き直す
- 再発防止: `test/outside-changes.test.ts`（`git rm` `mv` `add` の後／HEAD に在るが大きすぎる／シンボリックリンク越し／autocrlf）、`test/workspace-stamp.test.ts`（リンク越しの鍵／名前変更の元）、`test/outside-changed.test.ts`（前の回で落としたまま終えた／戻せなかったものを言う）
- 見つけ方: 押す前に別の担当に読ませた（21 件）。自分で見つけていたのは 6 件
