# 大きいモデルを分けて置く

メモリより大きいモデルを「大きすぎます」で断らず、GPU の VRAM・メモリ・SSD に分けて置いて動かします。
どう置くか（配置の計画）は、読む前に画面と doctor に出ます。どう置いても入らないときは、理由と、何があれば動くかを出します。

考え方は Strata（モデルを VRAM・RAM・SSD に分けて置き、置き方の計画を見せるツール）を見習いました。コードは写していません。
この中で読む道（inproc、`runtime.kind: "inproc"`）の GGUF が対象です。Ollama は置き方を自分で決めるので、計画は出しません。
llama-server を起こす道の計算は [32B級を動かすには](RUNNING-LARGE-MODELS.md) にあります。

## 使い方

1. アプリのウィンドウで ⚙（設定）→ モデル を開きます。
2. 置いてあるモデルの行に、この PC での具合が出ます。快適なものには何も足しません。

   | 具合 | 意味 |
   |---|---|
   | 快適 | 目安が 8 tok/s 以上 |
   | 動く（遅い） | メモリか VRAM に載るが、目安が 8 tok/s に届かない |
   | SSD から読む（とても遅い） | メモリに入り切らない分を、OS のページングで SSD から読む |
   | 入らない | どう置いても入らない。理由と、動かす手が出る |

3. 行の下の一行（「この PC では: GPU に 12/64 層、残りはメモリ。目安 3 tok/s。遅いですが、動きます」の形）が、どう置くかです。
   「計画を見る」を開くと、GPU の層・VRAM・メモリ・SSD から読む分・コンテキストウィンドウ・並列・バッチ・速さの目安・待つ上限が出ます。
4. 「これを使う」を押して、いつもどおり頼みます。選び直せば元に戻ります。計画は見せるだけで、何も書き換えません。
5. 取ってくる一覧（設定の「取ってくる」と、モデルのパネル）にも、取ってくる前に具合が出ます。
   入らないものは、モデルのパネルでは押せません（数十 GB を取ってから「入りません」にしないため）。理由と動かす手は、その下に出ます。

端末では `npm run doctor`（配った形では doctor の入口）の「モデル」の行に、同じ一行が出ます。

```
  ok   モデル   big.gguf: メモリより大きいので、分けて置きます。この PC では: GPU は使わず、メモリに載せて CPU で動かします、足りない分（…GB）は SSD から読みます。目安 … tok/s。とても遅いですが、動きます
```

## 置き方を選ぶ

同じモデルでも、動く置き方はいくつかあります。行の下に、選べる置き方が並びます（2 つ以上あるときだけ）。

| 置き方 | 中身 | 短所 |
|---|---|---|
| おまかせ（既定） | 上の「計画を立てる順」で決めたもの | 具合のとおり（遅い・とても遅い） |
| 速さを取る | コンテキストウィンドウを下限（4096）に、並列を 1 本に。GPU に載る層が増えるか、SSD から読む分が減る | 長い会話やファイルが、そこで切れる |
| 長く覚える | コンテキストウィンドウを、モデルが学習した長さ（上限 32768）まで開く | 遅くなる。メモリを多く使う |

1. どの置き方にも、速さ（実測か目安）・使うメモリ・短所が 1 行で付きます。既定には「（既定）」、選んであるものには「（選択中）」と出ます。
2. 置き方を 1 回押すと選べます。選んだものは覚えていて、次に読むときから使います。読んであるモデルは解いて、次の送信で読み直します。
3. 「おまかせ」を押すと、既定に戻ります。
4. 狭めても速くならない機械では、「速さを取る」ではなく「メモリを少なめに」と出ます。おまかせと変わらない置き方と、動かない置き方は並びません。
5. 快適で何も選んでいないモデルでは、「置き方を選ぶ」に畳んであります。

入らないモデルと、SSD から読むモデルには、動く形を先に出します。取ってくる一覧（`src/runtime/model-catalog.ts`）に在るものだけです。

| 動く形 | いつ出るか |
|---|---|
| 1 つ小さい量子化（「1 つ小さい量子化（q3_k_m・12.7GB）なら、全部メモリに入ります」の形） | 同じモデルの小さい量子化が一覧に在り、今の版より具合が上がるとき |
| 小さいモデル | 今の版が入らず、小さい量子化も無いとき。動くもののうち、いちばん大きいもの |

手元に無ければ「…を取ってくる」を 1 回押します。一覧に無い版は出しません。量子化の違う版は、GGUF を置く動かし方でだけ取ってこられます。

`npm run doctor` の「モデル」の行にも、同じ置き方が「置き方: おまかせ（既定）（選択中）: …」の形で出ます。
選んだ置き方は、データの下の `placement-choices.json` に在ります。設定の `runtime.contextSize` でコンテキストウィンドウを決めてあるときは、そちらを使います。

## 使うほど計画が当たる

速さの目安は見当で、当たりません。実際に読んで答えるたびに、読み込みの秒数と生成の tok/s を覚え、次の計画に使います。

- 一行と「計画を見る」と置き方の一行に、「実測 9.4 tok/s」か「目安 4.8 tok/s」かが出ます。実測が無い間は目安です
- 具合（快適・動く（遅い））と待つ長さも、実測の速さで決め直します。SSD から読む計画は、速くても「SSD から読む」のままです
- 覚えるのは、モデル（名前と大きさ）・置き方（GPU の層、SSD から読むか、コンテキストウィンドウと並列）・機械（VRAM と RAM）ごとです。機械の構成が変われば、別の覚えになります
- メモリの不足で落ちた段と、時間切れになった段も覚えます。次に読むときは、その段を最初から避け、記録に「前にメモリが足りずに落ちた置き方（…）を避けて、次の段から読みます」と出ます。
  全部の段が落ちた覚えなら、避けずに上から試します。30 日より前の覚えは使いません。読めたら、その段の覚えは消えます
- 覚えは、データの下の `placement-history.json` に 200 件までで、古いものから落とします
- 消すには `npm run clean`（配った形では clean の入口）。既定は一覧に「置き方の実測の記録 N 件」と出すだけで、`--yes` を付けたときだけ消します。消すと、目安に戻ります

## 大きいモデルは要るときだけ

普段は選んだモデルで答え、確かめで押し戻された頼みだけを、置いてある大きいモデルに回します。行き先を選ぶのはネットワークモデルです（[ネットワークモデル](NETWORK-MODEL.md) の「大きいモデルは要るときだけ」）。

1. ⚙（設定）→ モデル の「大きいモデルは要るときだけ」に、入り切りと、いま回すとしたらどこへ回るか（回せないなら理由）が出ます。
2. 既定は入りです。動く大きいモデルが置いてあるときだけ回ります。チェックを外すと切れ、もう一度押すと戻ります。
3. 回したときは、会話に「… → … に切替（押し戻しが 2 回続いたので、大きいモデルに回します）」と出て、記録（ui.log）にも残ります。
4. 置いて無い・計画で動かないときは回さず、会話に「大きいモデルに回しませんでした（理由）。今のモデルで続けます」と 1 行出ます。

| 何を | どう決めるか |
|---|---|
| 回す頼み | 最後の一言のあとに、押し戻し（確かめていない言い切り・やると言っただけ・合図なしで手を止めた、など）が 2 回続いた。または、確かめ（試験）が通らなかった差し戻しが 1 回在る |
| 大きいモデル | 取ってある中で、今のモデルより大きく、この PC の計画で動くもののうち、いちばん大きいもの。設定の `escalate.model` に名前を書けば、それ |
| 切る | 設定の画面のチェック（`escalate.enabled: false`） |

次の頼みは、また普段のモデルから始めます。モデルは一度に 1 つしか読まないので、回すときと戻るときに読み直しが入ります。

## 入らないとき

入らないと言うのは、次の 3 つだけです。どれも、あといくつ足りないかと、動かす手を言います。

| 理由 | 動かす手 |
|---|---|
| ディスクの空きが足りない（まだ手元に無いモデルを、保存先に置けない） | 保存先の空きを増やす。小さい量子化か、小さいモデルを選ぶ |
| メモリとページングの空きを足しても届かない | ページングの場所（swap・ページ ファイル）を増やす。メモリを足す。GPU のある機械で動かす。小さいモデルを選ぶ |
| 一つのテンソルが、メモリとページングを足した全部より大きい | メモリかページングの空きを増やす。小さいモデルを選ぶ |

ページングの空きが分からない機械では、断りません（分からないものを「無い」と決めません）。

## 仕組み

計算は `src/runtime/placement.ts`（ファイルも機械も読まない。機械を並べて試験できる）、
機械とモデルを読むのは `src/runtime/placement-machine.ts`、計画で読むのは `src/runtime/inproc.ts` の `#loadOn` です。

### 計画を立てる順

1. 全部を GPU に載せる。コンテキストウィンドウを狭めれば載るなら、狭めて載せる（一部でもメモリに回ると、速さが桁で落ちるため）
2. 載る層だけ GPU に載せ、残りはメモリに置く
3. メモリに入り切らないなら、コンテキストウィンドウを狭め（下限 4096）、並列を 1 本にする
4. それでも入り切らない分を、SSD から読む（メモリには固定しない）

4 でも届かないときだけ「入らない」になります。
VRAM は表示とドライバの分（600MB か 8% の大きい方）、メモリは OS とほかのアプリの分（2GB か 15% の大きい方）を空けて数えます。
GPU は、読む側が実際に使うもの（backend）で数えます。nvidia-smi に見えるだけの GPU では数えません。
層の数・学習したコンテキストウィンドウ・KV の大きさは GGUF の先頭から読み、読めないものは見当で数えて「見当」と出します。
速さの目安は、重みの在る場所の帯域から出した見当です。桁を見るためのもので、当たりません。

### 計画で読む

計画は、ライブラリ（node-llama-cpp）に渡す値になります。

| 計画 | 渡す値 |
|---|---|
| GPU の層（計画どおりの段） | `gpuLayers: { fitContext: { contextSize } }`（このコンテキストウィンドウが VRAM に入る範囲で、載るだけ。層の数え直しはライブラリに任せる） |
| GPU の層（段を下げたあと） | `gpuLayers: { max, fitContext }`。GPU を使わない段は `gpuLayers: 0` |
| SSD から読む | `useMmap: true`、`useMlock: false`、`ignoreMemorySafetyChecks: true`（ライブラリの「足りない」で断らせない） |
| コンテキストウィンドウ・並列・バッチ | `createContext` の `contextSize`・`sequences`・`batchSize` |

メモリに載る小さいモデルでは、今までどおり何も足しません。

### 落ちたら、段を下げて読み直す

メモリか VRAM が足りずに落ちたときだけ、上から順に試します。同じ中身の段は並べません。

1. 計画どおり
2. GPU に載せる層を半分に
3. コンテキストウィンドウを下限に・並列を 1 本に
4. GPU を使わず、メモリと SSD で

一段ごとに、記録に「読み込めませんでした（理由）」「やり直し 1/3: GPU に載せる層を 32 から 16 に減らして、読み直します」が出ます。
層の載せ方が変わらない段では、読んだ重みをそのまま使います。壊れたファイルのような、メモリの不足でない失敗は繰り返しません。
どの段でも落ちたら、読んだ重みを解いてから、最後の理由を返します。

### 待つ長さ

| 待ち | 決め方 | 過ぎたら |
|---|---|---|
| 読み込み | ファイルを遅いディスク（60MB/s）で読み切る長さの 2 倍。SSD から読む計画はその 4 倍。10 分より短くはしない | 読み込みを止め、「…の読み込みが N 分で終わりませんでした。ディスクが遅いか、メモリが足りずに行き来しています。小さいモデルか、空きの多い機械で試してください。」と返す。段を下げて繰り返さない |
| 最初の 1 トークン | コンテキストウィンドウを読み切る長さの 2 倍。10 分より短くはしない | 送り側（`src/providers/openai-compatible.ts`）が停滞として止める |
| 無音 | 1 トークンにかかる時間の 30 倍。120 秒より短くはしない | 同じ |

読み込みの上限は、こちらの時計で切ります。ライブラリが止める合図を見ない所で固まっても返り、遅れて届いた重みは解きます。
最初の 1 トークンと無音は、中で読む口が借りた直後に送り側へ言い（`: waits <ミリ秒> <ミリ秒>`）、送り側は自分の長さより長いときだけ延ばします。短くはしません。
最初の 1 トークンまでの間は、口からの合図（`: working`）が届くたびに待ち直すので、合図が届いている間はこの長さを超えて待ちます。
読み込みの返事は流れで返し（`/control/load`、一行ずつの進み具合と最後の一行の結果）、5 分を超える読み込みでも途中で切れません。

| 何を | どこで |
|---|---|
| 計算（機械を並べて、計画・待つ長さ・やり直しの段） | `test/placement.test.ts` |
| 読み方と渡す値（偽のライブラリ） | `test/large-load.test.ts` |
| 繋ぎ（計画が引数に効く・層を減らして読み直す・時間切れ・待つ長さ・画面の API・モデルのパネル・doctor） | `test/large-integration.test.ts` |
| 置き方を選ぶ（計算・覚え・読み込みの引数・画面の API・画面の部品・doctor） | `test/placement-options.test.ts` |
| 使うほど当たる（実測での置き換え・読めなかった段を避ける・上限・clean） | `test/placement-history.test.ts` |
| 大きいモデルは要るときだけ（押し戻しの数え方・行き先・大きいモデルの選び方・設定の API） | `test/escalate.test.ts` |
| 配った形の本体を、メモリの小さい機械として起こして、画面を押して答えを見る | `scripts/check-large.mjs`（CI の `large`） |

`scripts/check-large.mjs` は、本体を「メモリがモデルの 6 割の機械」として起こし、計画を見て、選んで、頼んで、答えを見ます。
そのあと本体を起こし直しながら、読み込みの最初の段を落として段を下げるのと、次はその段を避けるのと、読み込みの時間切れを見ます。
続けて、置き方を画面で選んで・その置き方で読んで・既定に戻すのと、速さが「実測」になり記録を消すと「目安」に戻るのを見ます。
最後に、押し戻しが続いた頼みが大きいモデルに回るのと、置いて無ければ回さずに 1 行で言うのと、設定で切れるのを見ます
（小さいモデルは `scripts/tiny-gguf.mjs --seed 7` で保存先に置き、終わったら消します）。
始める前に、本体のデータの下の実測の記録と選んだ置き方を消します（前の回の覚えで、結果が変わらないように）。
確かめは足すだけで、一度載せた id（`checks/large.ids`）は消しません（`test/large-checks.test.ts` が止めます）。

```
node scripts/check-large.mjs --start "<本体を起こす命令>" --port 4178 --model-file <.gguf の場所> --work <作業用のフォルダ> --shots <画像の置き場> --out <結果の json>
```

### 試験の口

大きいモデルの計画を、小さいモデルと普通の機械で確かめるための環境変数です。本物のメモリやディスクは変わりません。
立てなければ何も変わりません。普段は立てません。

| 環境変数 | 働き |
|---|---|
| `AAS_TEST_RAM_BYTES` | メモリを、この量として扱う（本物より大きくはしない） |
| `AAS_TEST_VRAM_BYTES` | 読む側が使う GPU の VRAM を、この量として扱う（本物より大きくはしない。GPU の無い機械に GPU は生えない。0 なら GPU なし） |
| `AAS_TEST_PAGING_BYTES` | ページングの空きを、この量の決まった大きさとして扱う |
| `AAS_TEST_DISK_BYTES` | ディスクの空きを、この量として扱う |
| `AAS_TEST_LOAD_TIMEOUT_MS` | 読み込みを待つ上限を、この長さにする |
| `AAS_TEST_LOAD_FAILS` | 読み込みの最初の N 段を、メモリが足りない形で落とす |
| `AAS_TEST_PUSHBACKS` | 頼みを、押し戻しがその回数あったものとして扱う（2 以上で、大きいモデルに回す道に入る） |

## 分かっていること・確かめていないこと

- 同梱のエンジンは、CPU で動かす重みを読み込むときに並べ直し、ファイルの写し（mmap）ではなく普通のメモリに置く、という前提で数えています（`weightsNeedRam`）。
  だから、メモリを超えた分は OS のページング（Windows のページ ファイル、Linux の swap）が SSD へ出し入れし、ページングの空きが無い機械では入らないと言います。
  この前提と、`src/runtime/placement.ts` の頭に書いてある測った値（9B を上限 3GB で読ませて止められた・4 コアで 2 tok/s 台）は、前の作業から引き継いだもので、測った記録の文書はリポジトリにありません。今回は確かめ直していません
- Windows のページ ファイルは、既定の「システム管理」で広がるものとして数えています。手で止めてある機械は見分けていません（私の推測）
- 取ってくる一覧のファイルの大きさは、4B・9B・27B（3.5 と 3.6）・35B-A3B の 5 つを配布元の返す大きさと照らし、`src/runtime/model-catalog.ts` の値と同じでした。層の数と KV の大きさは写してある値のままで、照らし直していません
- 本物の大きいモデル（メモリを本当に超えるもの）と、本物の GPU（VRAM が足りずに落ちる所）では確かめていません。段を下げて読み直すのと時間切れは、偽のライブラリと試験の口で見ています
- Windows の実機では確かめていません。CI の `large` は回していません
- `check-large.mjs` の `large-followup-reads-only-new`（続けて頼むと、読むのは新しい分だけ）は、待ちの秒数で見ていた間、0.1 秒の差で通る回と落ちる回がありました。
  いまは、その回の呼び出し全部が新しく読んだトークンの数（記録の「新しく読んだのは N トークン」）の合計で見ます。数で見ると落ちます（1 回目 669、2 回目 680）。
  本体は、1 回の頼みで中のモデルを 3 回呼び、口が 1 本なので、前の頼みの続きを毎回上書きしています（2 回目の答える呼び出しは、入力 258 トークンのうち 254 トークンを読み直していました）。
  補助の呼び出し（要る事実を挙げる・指摘かどうかを判じる・検問）は、会話とは別の小さな context の口（補助の口）で回すように直しました（docs/DECISIONS.md 217 回目）。
  直したあとは、2 回目の頼みの答える呼び出しが読むのは 297 トークンのうち 63 トークンで、合計は 1 回目 675、2 回目 453 です（配る形・Qwen3-0.6B）。
  補助の口は、最初の補助の呼び出しで開き、コンテキストウィンドウ 1024 の分の KV（Qwen3-0.6B で目安 112MB）が余計に要ります。計画の数字には入れていません。
  小さいモデルの答えは回によって外れることがあり（2 回のうち 1 回は 6006652）、その回は確かめが落ちます
- 画面の計画と、読むときの計画は、コンテキストウィンドウの望みと VRAM の空きの見方が違います。GPU に一部だけ載る機械では層の数がずれ、実測が当たらないことがあります（数層のずれまでは当てます）。本物の GPU では確かめていません
