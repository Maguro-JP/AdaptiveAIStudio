# 最も効率の良いモデル運用

> **注意:** ここでいう「効率」はコスト削減ではない。
> ローカルにトークン単価は無いので、節約する対象がそもそも無い。
> 唯一の指標は **1件を完了させるまでの実時間**。
> 計算資源を使い切って速く終わらせる方針は [パフォーマンスで戦う](PERFORMANCE.md) を参照。

## 0. 前提が変わる

クラウドAPIでは、モデル選択は**コストと品質の綱引き**だった。
安いモデルで済むところは安いモデルで、というのが定石。

**ローカルにはこの綱引きが無い。** トークン単価がゼロだから。

したがって、小さいモデルを選ぶ理由は「安いから」ではなく
「速いから」しか残らない。そして速さの指標は tok/s ではない。

> 本当の指標は **1件のタスクを完了させるまでの実時間**。

## 1. 素朴な直感が間違う

「小さいモデルは速いから、簡単な作業は小さいモデルに回そう」

これは**しばしば損になる**。理由は3つ。

### 1.1 やり直しが効く

弱いモデルは速いが失敗する。失敗すればやり直す。

```
期待実時間 = 生成時間 ÷ 成功率
```

7B が 41 tok/s で成功率20%、32B が 3 tok/s で成功率93% のとき
（1200トークンの作業）:

| | 生成時間 | 成功率 | 期待実時間 |
|---|---|---|---|
| 7B | 29秒 | 20% | **146秒** |
| 32B | 400秒 | 93% | **430秒** |

この条件では 7B が勝つ。**やり直し算だけなら、速い方が有利**。
これは正しい計算で、本プロジェクトもそう計算する。

### 1.2 だが「見逃し」が入ると逆転する

弱いモデルの本当の危険は、失敗することではない。
**間違ったまま通ってしまうこと**。

失敗ならその場でやり直せば済む（安いミス）。
だが誤りが検査をすり抜けると、後でデバッグと手戻りが発生する（高いミス）。

```
期待実時間 = 生成時間 ÷ 成功率 + 見逃し率 × 手戻りコスト
```

同じ7Bで、通った3件のうち2件が後で誤りと判明したなら:

| | やり直し込み | 見逃しコスト | 合計 |
|---|---|---|---|
| 7B | 146秒 | 40% × 30分 = 720秒 | **866秒** |
| 32B | 430秒 | 0% | **430秒** |

**逆転する。** 32B の方が速い。

手戻りコストの既定値は30分。生成時間より桁で大きいのが普通なので、
見逃し率が数%あるだけで判断が変わる。

### 1.3 モデル切替コストが効く

VRAM 8GB では複数モデルを同時に載せられない。
「この作業だけ小さいモデルで」をやると、**アンロード→ロードで数十秒〜数分**かかる。

短い作業ほど、この切替コストが生成時間を上回る。

```
今 32B がロード済み、80トークンの短い作業:
  32B のまま実行      : 27秒
  7B に切り替えて実行 : 2秒 + 切替60秒 = 62秒  ← 損
```

**「今ロードされているモデルで済ませる」が正解になる場面が多い。**

## 2. だから、利用者に選ばせない

**モデル選択は利用者の仕事ではない。** 自動操縦が裏で常に最適化する。

```
起動
  ↓ マシンを検出 (GPU / VRAM / RAM)
  ↓ 入っているモデルを列挙
  ↓ それぞれの実行計画を計算（GPU層数・context・速度）
  ↓ 期待実時間で順位づけ（やり直し・見逃し・切替コスト込み）
  ↓ 最良を選び、理由を表示
作業
  ↓ 結果を記録（成功 / 失敗 / 見逃し / 実測tok/s）
  ↓ より良い選択肢が出てきたら裏で乗り換え
```

設定ファイルにモデルを書く必要はない。

```
担当モデル: ollama:qwen3:30b-a3b
  起動時の自動選択 — 25 tok/s で 48秒 / 成功率 65%(事前値) / 見逃し 18% / 1件あたり約458秒
```

### 明示指定は「検証用」であって既定ではない

低スペックモデルに縛って使うのは、比較検証をする人の用途。
そういう人は Ollama や LM Studio を直接使えばよい。
本ツールが提供すべきは **何も考えなくても最良で動くこと**。

```jsonc
// 通常運用: 何も書かない
{ "providers": [ ... ] }

// 検証用: 固定したいときだけ
{ "candidates": ["ollama:qwen2.5-coder:7b"] }
```

### 乗り換えの暴れを防ぐ

わずかな差で載せ替え続けると、切替コストだけを払うことになる。
一定の改善幅（既定25%）を超えたときだけ乗り換える。

### 原則1: 既定は「その環境で動く最良のモデル1つ」

節約する理由が無いので、**最初から一番強いモデルを載せる**。
小さいモデルへ降りるのは、実測でそれが速いと分かった場合だけ。

基準環境 (RTX 4060 8GB / RAM 32GB) での既定候補:

| 優先 | モデル | 速度 | 理由 |
|---|---|---|---|
| **1** | qwen3:30b-a3b (MoE) | 33 tok/s | 30B級の質を7B並みの速度で出す。この環境の最適解 |
| 2 | qwen2.5-coder:14b | 10 tok/s | MoEが使えない場合の現実的な線 |
| 3 | qwen2.5-coder:32b | 3 tok/s | 質を最優先し、時間を許容する場合 |
| 4 | qwen2.5-coder:7b | 41 tok/s | 速度が要る定型作業のみ |

**7Bを既定にしない。** ローカルで7Bを既定にするのは、
クラウドの節約癖をそのまま持ち込んでいるだけ。

### 原則2: モデル数を増やさない

「役割ごとに最適なモデルを」は、**切替コストを無視した理想論**。
VRAMが厳しい環境では、載せ替えの合計時間が利得を食い潰す。

| 環境 | 推奨 |
|---|---|
| VRAM 8GB | **1モデル常駐**。全職能を兼任させる |
| VRAM 16GB | 2モデル常駐（大=判断 / 小=定型）まで |
| VRAM 24GB+ | 職能ごとの使い分けが現実的になる |

複数モデルが正当化されるのは、
**同時に常駐できる** か **1つのレーンにタスクがまとまって溜まる** 場合だけ。
スケジューラは後者のために、
今ロード済みのレーンを優先してタスクを流す（実装済み）。

### 原則3: 推測せず、実測で決める

成功率も速度も、環境とタスクの性質で変わる。
一般論ではなく**自分のPCの実績**で決める。

`.aas/metrics.json` に蓄積する:

```
モデル                        実測tok/s  成功率  試行  1件完了まで
qwen3:30b-a3b                     31.2    82%    45  約48秒
qwen2.5-coder:7b                  40.0    20%    10  約50秒
qwen2.5-coder:32b                  3.1   100%    12  約155秒
```

十分な試行が溜まるまでは事前値と混ぜ、1回の失敗で判断が振れないようにする。

### 原則4: 検査を挟むと、弱いモデルの価値が上がる

見逃しコストが高いのは、誤りが検知されないから。
**検査担当を挟めば見逃し率が下がり、弱いモデルでも安全に使える。**

```
作業者(7B, 速い) → 検査(32B, 遅いが確実)
```

検査は生成より短い（差分を読むだけ）ので、遅いモデルでも負担が小さい。
これが「役割分担」が効く数少ない正当な場面。

ただし2モデル必要なので、VRAMに余裕があるか
MoEのように1つで両立できる場合に限る。

## 3. 実装

| 部品 | 役割 |
|---|---|
| `src/runtime/planner.ts` | モデル諸元とマシン諸元から実行設定と速度見積りを計算 |
| `src/runtime/efficiency.ts` | 期待実時間でモデルを順位付け（やり直し・見逃し・切替コスト込み） |
| `src/runtime/metrics.ts` | 実測の蓄積。成功率・見逃し・実測tok/s・ロード秒数 |

```ts
choose({
  candidates: [
    { modelId: 'local:qwen3:30b-a3b', plan, stats, loaded: true },
    { modelId: 'local:qwen2.5-coder:7b', plan, stats, loaded: false },
  ],
  expectedTokens: 1200,
});
// → { modelId, expectedSeconds, successRate, defectRate, reason }
//   reason: "31 tok/s で 39秒 / ロード済み / 成功率 82%(実測) / 見逃し 9%"
```

選択理由を必ず言葉で返す。**なぜそのモデルが選ばれたか分からない自動選択は、
調整もできず信用もできない。**

## 4. まとめ

- ローカルには単価が無い。**節約のために弱いモデルを使う理由はゼロ**
- 速さの指標は tok/s ではなく **1件完了までの実時間**
- 弱いモデルの危険は失敗ではなく**見逃し**。ここを数えないと判断を誤る
- VRAMが厳しいうちは**モデルを増やさない**方が速い
- 一般論ではなく**自分の環境の実測**で決める
