# 自前化と、クラウド解禁の条件

## 1. 今の立ち位置（意図的な借り物）

開発速度を優先し、現時点では既存の実装を流用している。

| 領域 | 現在 | 依存の性質 |
|---|---|---|
| 推論ランタイム | Ollama / llama.cpp / **この中で読む** | Ollama は借り物。他の二つは自前で持っている。設定で切り替える |
| モデル | Qwen / Llama 等 | 借り物で構わない。**モデルは交換可能な資源**であり、自作対象ではない |
| Provider契約・エージェント・スケジューラ | 自前 | 既に自前 |

**モデルそのものを自作する意図はない。** 自前化の対象は
「モデルをどう動かすか」の層であって、モデルではない。

## 2. なぜ自前化するのか

> 上流の不具合対処待ちで開発が止まるなら、オリジナルで作っている意味がない。

これは本プロジェクトの根本方針（サービス依存で止まらない）の、
ローカル版の言い換えである。Ollama への依存は、
Claude への依存と構造的に同じ問題を持つ。

具体的に困る場面:

- Ollama が特定のモデル形式・量子化に未対応
- オフロード層数の自動判断を誤り、起動失敗やOOMになる（制御できない）
- 修正が上流に取り込まれるまで待たされる
- API仕様が変わる / プロジェクトが停止する

## 3. 自前化の順序

**一度に置き換えない。** 既に `LocalRuntime` 抽象の裏に置く設計にしてあるので、
段階的に自前実装へ寄せられる。

| 段階 | 内容 | 得られるもの |
|---|---|---|
| ~~S1~~ | ~~llama.cpp を直接子プロセスとして起動する Runtime~~ | **完了**。`n_gpu_layers` / KVキャッシュ量子化 / mmap をプランナの計算値で指定できる |
| ~~S4'~~ | ~~この中で読む（`inproc`）~~ | **完了**。実行ファイルを増やさずに GGUF を読む。何も入れられない機械で動く |
| **S2** | 自前のモデル管理（ダウンロード・検証・カタログ・VRAM見積り） | モデルの入手経路を Ollama に依存しない |
| **S3** | 自前のプロセス常駐管理（ロード/アンロード・レーン割り当て・並列制御） | レーン方式を自分で最適化できる |

S1 と S3 で、実務上の困りごとはほぼ解消する。

### S4' — この中で読む（`inproc`）

順番を飛ばして先にやった。**そうしないと動かない場所があったため。**

会社の PC は、アプリ自身の土台（`node.exe`）以外の実行ファイルを置けない。
`llama-server` を起こす道（S1）は、そこで止まる。NetVision が同じ壁に当たって
既に選んでいた答え（`lib/` のライブラリで中で読む）を、こちらへ持ってきた。

- `src/runtime/inproc.ts`。`node-llama-cpp` は中身が `.dll` と `.node` だけで
  `.exe` は0個（実測）
- 上の層は OpenAI 互換の口しか見ないので、その口を**自分の中に立てる**
  （127.0.0.1 のみ。外へ出る口は増えない）
- GGUF は同梱しない。置き場に置いてあるものを読む

これは S4（バインディングを自前で持つ）ではない。**上流のものを使っている。**
自前で持つ必要が出るのは、上流の修正待ちで詰まったときだけ。

### 並行開発する

自前実装が完成するまで既存を使い続ける、ではなく、
**両方を `LocalRuntime` の実装として並存させ、設定で切り替える。**

```jsonc
{ "runtime": { "kind": "ollama" } }    // 安定。日常運用（既定）

{ "runtime": {                          // 自前。限界を攻める / 検証
  "kind": "llamacpp",
  "command": "llama-server",
  "modelsDir": "C:/models",
  "parallel": 2
} }
```

`npm run models` で、各GGUFがこのPCでどう動くかを起動前に確認できる。

こうすると自前実装が未完成でも開発が止まらず、
出来たところから実運用に混ぜていける。
片方が壊れてももう片方で動く、という点でも方針と一貫している。

## 4. クラウド（Claude API / Claude Code CLI）を解禁する条件

現在は既定で無効。**無駄遣いになるため、運用フェーズまで有効化しない。**

解禁の判断基準を、感覚ではなく条件として決めておく。

### 前提条件（すべて満たすこと）

1. ローカルのみで日常的に開発が回っている（運用フェーズに入っている）
2. **既存ツールより優れている点が、少なくとも1つ実証されている**
3. その優位性がクラウドを混ぜることで損なわれない

### 「既存より優れている点」の候補

自分たちの実測で確認できるもの。

| 候補 | 測り方 |
|---|---|
| 制限で止まらない | 連続稼働時間。既存ツールが制限に達する作業量を完走できるか |
| 載らないモデルが動く | 32B級を部分オフロードで実行し、実際に成果物が出るか |
| 並列で速い | 同じ依頼を、単一エージェントと並列チームで比較（総所要時間） |
| 役割分担で質が上がる | 検査担当を挟んだ場合と挟まない場合で、テスト通過率を比較 |

このどれか1つでも既存を上回れば、クラウドを足す価値がある。
**逆に1つも上回らないうちにクラウドを混ぜると、
「結局クラウドが賢いだけ」になり、何を作っているのか分からなくなる。**

### 解禁後の使い方

解禁しても、**主従は変えない**。

- ローカルが主。クラウドは「統制・PM など判断の重い職能」に限定して配置する
- クラウドが使えなくなっても、ローカルだけで完走できる状態を維持する
- クラウドはVRAMを消費しないので、並列の逃がし先としても有効

## 5. 現時点で守っていること

- クラウドProviderは設定で `enabled: false`（既定）。登録も接続もしない
- ローカルのみで全機能（チャット・エージェント・並列チーム）が動作する
- Claude Code CLI 連携は未実装。`ChatProvider` 契約はHTTPを前提にしていないため、
  子プロセス方式のアダプタを後から追加できる（口だけ用意されている状態）
