# GGUF を直接読む

これまでモデルの諸元は、名前からの推測か Ollama の申告に頼っていた。
「32B と名前に入っているから 32B だろう」は、当たることも外れることもある。
外れたまま「載る／載らない」を計算しても意味がない。

ファイルの先頭には、層数も、ヘッド数も、文脈長も、
テンソルごとの量子化形式まで書いてある。読めば済む話だった。

## 何が変わるか

| | これまで | これから |
|---|---|---|
| 層数 | 名前から推測 | ファイルに書いてある値 |
| KVヘッド数 | GQA を考慮できず | `head_count_kv` をそのまま |
| ヘッド次元 | 推測 | 埋め込み次元 ÷ ヘッド数 |
| 量子化 | ファイル名の `q4_k_m` を頼りに | テンソルの実際の形式 |
| MoE | 名前で判別 | `expert_count` / `expert_used_count` |

KVキャッシュ量も、部分オフロードの層あたりバイト数も、
この四つが正しくないと全部ずれる。

## 分からないものを埋めない

これが設計でいちばん大事にしたところ。

この読み取りは**仕様の理解に依っている**。理解が一つ違えば値が狂う。
狂った値を自信たっぷりに返すと、その先の計算が全部狂う。
しかも計算が通ってしまうので、**間違いに気づけない**。

だからこうした。

- 知らない値の型に出会ったら、その先は位置が分からないので**そこで読むのをやめる**
- 必要な値が一つでも欠けたら、**諸元を返さない**（名前からの推測に落ちる）
- 表に無い量子化のビット数は**推測しない**
- 読めなかったところは全部 `warnings` に残す。黙って捨てない

推測で埋めた数字より、空欄の方が安全。

```
# 諸元にはできませんでした
  足りない: embedding_length（埋め込み次元）
  足りない: 量子化形式（テンソル一覧が読めていません）
  推測で埋めない方針のため、ここは空のままにします。
```

## 本物で確かめる

**この読み取りは、まだ本物の GGUF で確かめていない。**

試験で使っているのは「仕様の理解どおりに書いた GGUF」なので、
理解が間違っていれば、試験も一緒に間違える。自分で自分を採点している状態。

だから目で確かめる手段を用意した。

```
npm run models -- --inspect <手元の .gguf>
```

手元に GGUF が無ければ、`npm run models -- --get` で取ってこられる。

以下は前の世代のモデルで出したときの例。
**名前が古いのは承知のうえで、そのままにしてある** —
層数や次元はその版の実際の値なので、名前だけ差し替えると数字が嘘になる。

```
qwen2.5-7b-instruct-q4_k_m.gguf  (4.70 GB, GGUF v3)

# 書いてあったこと
  アーキテクチャ        qwen2
  名前                  Qwen2.5 7B Instruct
  層数                  28
  埋め込み次元          3584
  ヘッド数              28
  KVヘッド数            4
  文脈長                32768

# テンソル
  読めた数              291
  主な量子化            Q4_K（実効 4.83 bit/重み）

# 諸元として解釈した結果
  パラメータ数          約 8.4B
  ヘッド次元            128
  KVヘッド数            4
```

値がおかしければ、この出力をそのまま知らせてほしい。直せる。

## 読む量

先頭 16MB だけ読む。数GBのファイルを丸ごと抱えない。
テンソルが多いモデルでは一覧が途中までになるが、そのことは `warnings` に出る。
主な量子化の判定には十分な数が読めている。

## どう使われるか

`llamacpp` ランタイムがモデル一覧を作るときに、ついでに読む。
読めた諸元は実行計画（何層をGPUに載せるか、文脈をどこまで伸ばせるか）に使われる。

信じる順番は **書いてあるもの > 登録済みの諸元 > 名前からの推測**。
読めなければ黙って推測に落ちるので、これまでより悪くなることはない。
