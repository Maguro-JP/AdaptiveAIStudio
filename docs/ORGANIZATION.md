# 組織設計 — AdaptiveAIStudio を「会社」として動かす

## 0. 前提の訂正

初版では役割を `coding` / `japanese` / `vision` のように分類していた。
これは **モデルの特性による分類** であって、**職能による分類ではない**。

正しくは、組織はまず職能で構成される。

- 職能 = 何をする人か（窓口・統制・PM・部署リーダー・作業者・検査）
- モデル = その職能に割り当てられる **人材（リソース）**

「日本語が得意なモデル」は職種ではなく、
「客先窓口という職能に、言語化の上手い人材を配置する」という話になる。
以降はこの区別を守る。

---

## 1. 組織図

                   ┌────────▼────────┐
                   │  窓口 (Intake)   │  言語化・傾聴・復唱

## 2. 職能の定義

職能は「責務・持つ権限（ツール）・成果物」の3点で定義する。
モデル名はここに登場しない。

| 職能 | 責務 | ツール権限 | 成果物 |
|---|---|---|---|
| `intake` 窓口 | 曖昧な依頼の言語化。復唱して確認 | なし（会話のみ） | 依頼書ドラフト |
| `control` 統制 | 受理判断・優先度・体制決定・最終検収 | 読み取りのみ | 体制指示 / 検収結果 |
| `pm` 要件定義 | 作業分解・受入条件の明文化・依存関係の整理 | 読み取り・探索 | 作業指示書（DAG） |
| `lead` 部署リーダー | 担当タスクの詳細化・作業者への割り当て・一次レビュー | 読み取り・探索 | サブタスク / 一次レビュー |
| `worker` 作業者 | 実装・修正・調査。**実際に手を動かす唯一の職能** | 読み書き・コマンド実行 | 差分 / 調査結果 |
| `reviewer` 検査 | 受入条件との突合。批判的レビュー | 読み取り・テスト実行 | 合否 + 指摘 |
| `scribe` 記録 | 決定事項・ルールの記録 | 記録領域への書き込み | プロジェクト記憶 |

**手を動かすのは `worker` だけ。** これを守らないと、
全員がファイルを書いて衝突する。会社と同じ。

## 3. 部署（Department）

部署は「領域」であり、職能とは直交する。
部署はリーダー1名と作業者N名を持つ。

```jsonc
{
  "departments": {
    "impl":   { "name": "実装部", "lead": "...", "workers": ["...", "..."] },
    "design": { "name": "設計部", "lead": "...", "workers": ["..."] },
    "qa":     { "name": "品質部", "lead": "...", "workers": ["..."] },
    "docs":   { "name": "文書部", "lead": "...", "workers": ["..."] }
  }
}
```

部署は設定ファイルで自由に増減できる。コード変更は不要とする。

## 4. 人材配置（モデルの割り当て）

各ポストに **モデル候補列** を割り当てる。列の中は従来どおり
可用性フォールバック（前が使えなければ次）。

```jsonc
{
  "staff": {
    "intake":       ["ollama:qwen2.5:14b", "claude:claude-opus-5"],
    "control":      ["claude:claude-opus-5", "ollama:qwen2.5:14b"],
    "pm":           ["claude:claude-opus-5", "ollama:qwen2.5:14b"],
    "impl.lead":    ["ollama:qwen2.5-coder:14b", "claude:claude-opus-5"],
    "impl.worker":  ["ollama:qwen2.5-coder:7b"],
    "qa.reviewer":  ["ollama:qwen2.5-coder:7b", "claude:claude-opus-5"],
    "design.worker":["ollama:llava:7b"]
  }
}
```

これで **「職能 × 部署 × 可用性」の三軸** になる。
「この作業者はコーディング特化モデル」「窓口は会話が自然なモデル」
という配置は、この表を書き換えるだけで変わる。

## 5. 並列実行の設計 — ここが「いっぱい働かせる」の核心

### 5.1 誤解しやすい点

「たくさんのモデルを同時に載せる」＝並列ではない。
VRAM 8GB では 7B/Q4 が2つでほぼ埋まる。
**モデル数を増やす方向で並列度を稼ぐのは、この環境では行き止まり。**

正しい稼ぎ方は **同じモデルへ複数タスクを同時に流すこと**。
Ollama / vLLM は同一モデルへの並列リクエストをバッチ処理でき、
VRAM追加消費はKVキャッシュ分だけで済む。
つまり **作業者7人が同じ1つのモデルを共有して同時に働く** のが最も効率的。

### 5.2 レーン方式

同時にロードするモデルを「レーン」と呼び、レーン数を絞る。
レーン内は並列度を上げる。

```
レーン1: qwen2.5-coder:7b   (VRAM ~5.5GB)  並列4  ← impl.worker / qa.reviewer
レーン2: CPU実行の小型モデル (RAM)          並列2  ← scribe / 単純な要約
レーン3: クラウド (Claude)   (VRAM 0)       並列4  ← control / pm（使えるとき）
```

- レーンの切替（アンロード→ロード）は数秒〜十数秒かかる **高コスト操作**
- スケジューラはタスクをレーン単位でまとめ、切替回数を最小化する
- クラウドはVRAMを消費しないので、並列の逃がし先として非常に有効

### 5.3 スケジューラ

PM が出す作業指示書は **依存グラフ(DAG)**。
スケジューラは依存が解けたタスクを、レーンの空き枠へ流し込む。

```
タスクA(impl) ─┐
タスクB(impl) ─┼→ タスクD(qa) → 検収
タスクC(docs) ─┘

レーン1(coder, 並列4): A, B を同時実行 → 完了後 D
レーン2(CPU,   並列2): C を並行実行
```

制約:
- レーンごとの最大並列数は設定値（初期値はVRAMから自動推定）
- 同一ファイルを書く作業者は同時に走らせない（**書き込みロック**）
- 総同時実行数の上限も設ける（CPU/メモリの保護）

## 6. 会話の往復をどう扱うか

「ユーザーと詰める」「リーダーと相談する」は、
**明示的な往復フェーズ**としてワークフローに組み込む。

```
1. intake   : 依頼を復唱し、不明点を列挙
2. → ユーザー: 確認（ここで止まる。勝手に進めない）
3. pm       : 分解し、受入条件を書く
4. pm ↔ lead: 各部署リーダーに実現可能性を照会（並列）
5. pm       : 見積りと体制を確定
6. → ユーザー: 作業指示書を提示して承認を得る（ここで止まる）
7. 実行フェーズ（並列）
8. control  : 検収
9. → ユーザー: 差分を提示して承認を得る（ここで止まる）
```

**止まる場所を3箇所に固定する。** これが無いと、
勝手に大量のファイルを書いて収拾がつかなくなる。

## 7. 可観測性 — 誰が何をしているか見える

多数のモデルが並列で動くと、何が起きているか分からなくなる。
これは機能ではなく **必須要件** とする。

```
統制  claude-opus-5      検収待ち
PM    claude-opus-5      完了 (12.4s / 3,200tok)
実装部
  ├ リーダー qwen-coder:14b  割当中
  ├ 作業者1  qwen-coder:7b   実装中 src/auth.ts    ████░░ 
  ├ 作業者2  qwen-coder:7b   実装中 src/session.ts ██░░░░
  └ 作業者3  qwen-coder:7b   待機（レーン1が満杯）
品質部
  └ 検査1    qwen-coder:7b   待機（依存: 作業者1）
```

各タスクに **担当ポスト・使用モデル・所要時間・トークン数** を必ず記録する。
これは「どの配置が効率的か」を後から調整するための実測データにもなる。

## 8. 実装順序（P1〜P3 の再定義）

| 段階 | 内容 | 完了条件 |
|---|---|---|
| **P1** | ツール実行ループ + `worker` 1名 | 1つのモデルがファイルを読み、差分を出し、承認後に書ける |
| **P2** | レーン + スケジューラ + 並列作業者 | 同一モデルで作業者3名が同時に別ファイルを実装できる |
| **P3** | `pm` によるDAG分解 + `lead` + `reviewer` | 1つの依頼が自動で分解され、並列実行され、検査を通る |
| **P4** | `intake` / `control` + 3箇所の承認ゲート | 曖昧な依頼から検収まで、組織として一周する |
| **P5** | 可観測性UI（§7の画面） | 誰が何をしているか一目で分かる |

P1 を飛ばして組織を作ると、**指示だけして誰も手を動かせない会社**になる。
まず作業者1名を確実に動かす。

## PM — 依頼を作業指示書に分解する

`/plan <依頼>` で、依頼が複数の作業指示に分解され、担当が割り当てられ、
依存関係が解けたものから同時に走り出す。

```
方針: 設定の読み込みに検証を足す
  [t1] scout @fast （すぐ着手）
      現在の設定読み込みを読み、検証されていない項目を列挙する
  [t2] worker @strong ← t1 の後
      列挙された項目に検証を足す
      書き込み: src/config.ts
  [t3] tester @fast （すぐ着手）
      設定の検証について、いま通っている試験を確認する
```

`t1` と `t3` は同時に走る。`t2` は `t1` の完了を待つ。
同じファイルを書く件どうしは、依存が無くても自動で直列化される（書き込みロック）。

### 権限は担当から降りてくる

各件の `roleId` から、その担当の気質（system）と権限（tools）が決まる。
`scout` は調べる担当なので、そもそも書き込むツールを渡されない。
禁じているのではなく、配っていない。

### 計画は信用せず、直す

モデルは平気で壊れた計画を返す。存在しない担当を指名し、依存を循環させ、
同じ ID を二度使う。そのまま流すと全件が未実施になる。

| 壊れ方 | 直し方 |
|---|---|
| 存在しない担当 | 引き受け役に替える |
| 存在しないレーン | 割り当て直す |
| ID の重複 | 付け替える |
| 存在しない依存・自分待ち | 外す |
| 依存の循環 | 戻り辺を落とす |
| 分け過ぎ | 上限まで絞る |
| 指示が空 | その件を外す |
| 書き込み先の表記揺れ | 揃える（揃っていないと錠が効かない） |

直した内容は必ず表示する。黙って直すと、次も同じ壊れ方をする。

### 分解できなくても止まらない

JSON が返ってこなくても、モデルの呼び出しごと失敗しても、
**一人で全部引き受ける一件**に畳んで先へ進む。
分解できないことは、作業をしない理由にならない。

## 検収 — 人に見せる前に、一度受け取る

分解して並列に走らせられるようになると、次に困るのは
「で、結局どうなったのか」が分からなくなることだ。
五人が同時に動いた結果を、人が五本の作業ログから読み取るのは無理がある。

だから間に受け取る人を置く。会社で言えば統制にあたる。やることは三つ。

1. 誰が何をしたかを一枚にまとめる
2. 出てきたものを検査に通す
3. **人が見るべき点だけを挙げる**

3 が肝。全部を人に見せるなら、間に人を置く意味が無い。

```
検収: 判断をお願いします
  依頼: 設定の読み込みに検証を足す
  方針: 検証を足す
  作業: 2/3件完了 / 検査: 通過
    ✓ [t1] scout  検証されていない項目は3つでした
    ✓ [t2] worker 3項目に検証を追加しました
    − [t3] tester
  変更: 2件
    src/config.ts
    test/config.test.ts
  見ていただきたい点:
    [確認] 1件が実施されていません。依頼の一部が手つかずです。
        t3: 依存タスクが失敗しました: t2
    [確認] 計画に無いファイルが変わっています（1件）。
        test/config.test.ts
```

### 判断はモデルにさせない

検収の判断に推論は使わない。理由は二つ。

- 判断の根拠が毎回変わっては、検収にならない
- **作った本人に採点させない**

拾うのは次の五つ。すべて事実の照合で決まる。

| 見るもの | なぜ |
|---|---|
| 失敗した件 | 言うまでもない |
| **未実施の件** | 失敗より見落としやすい。何も起きないため |
| 検査の結果 | 通っていないものを人に見せない |
| **計画に無い書き換え** | 「ついでに直した」か「勘違いして触った」か。後者が危ない |
| **何も変わっていない** | 成功に見えて何も起きていないのが、一番たちが悪い |

### 何が変わったかは、宣言ではなく実際を見る

計画の `writes` は自己申告に過ぎない。
実際に変わったものは、書き込みツールの実行記録と git の前後比較の
両方から取る。コマンド経由で書き換えられた分も、これで拾える。

作業前から検査が落ちていた場合は、最初に控えておいて切り分ける。
前から壊れていたものを今回の失敗として報告しない。

## 一人に任せない

これはモデルの数を増やす話ではない。
**同じ対象に、違う気質が、複数回当たる**という話。

書いた本人は自分の書いたものを疑えない。
一度調べただけの話は、まだ裏が取れていない。
検査も、情報収集も、回数を重ねるほど精度が上がる。

だから計画には、依頼に書かれていない工程が必ず足される。

| 元の件 | 足される工程 |
|---|---|
| 書き換える件 | 別の気質の担当が、**実際に動かして**確かめる |
| 調べただけの件 | 別の担当が、**別の材料で**裏を取る |

```
  [t2] worker @strong ← t1 の後   3項目に検証を追加
  [t2_2] breaker @fast ← t2 の後  書かれたものを実際に動かして確かめる
```

### 頼むのではなく、構造にする

「検査も入れてね」とモデルに頼む形にはしない。頼みは守られないことがある。
計画を組み立てる段階で**必ず入る**ようにすれば、守られる。
ハーネスの考え方と同じで、行儀ではなく仕組みで担保する。

### 確かめる人は順に回る

真面目な検査役だけでは足りない。

- 手順通りに試す人（TESTER）
- わざと外れた使い方をする人（GREMLIN）
- 書かれたものを読み直す人（CURATOR）
- 悪用を考える人（SENTINEL）

見えているものが違うので、回すほど拾える範囲が広がる。
いつも同じ人が見ることにならないよう、順に交代する。

### 確かめる人は書かない

確かめる工程には書き込み権限を渡さない。
指摘するところまでが仕事で、直すのは別の工程になる。
見つけた人がその場で直すと、直したものを誰も見ていないことになる。

### 増えすぎない

足す工程を含めて、上限の2倍で打ち止める。
確かめることが目的化して、確かめる工程を確かめ始めたら本末転倒なので。
