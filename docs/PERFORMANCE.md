# パフォーマンスで戦う

## 0. 前提の再確認

ローカルLLMは、モデルの賢さでは大手クラウドに負ける。
これは当面ひっくり返らない。だからそこで戦っても勝てない。

一方で、ローカルには**クラウドが構造的に持てない資産**がある。

| | クラウド | ローカル |
|---|---|---|
| トークン単価 | かかる | **ゼロ** |
| 利用制限 | ある | **無い** |
| 同時実行 | 課金で青天井だが金がかかる | **ハードの上限まで無料** |
| 常時稼働 | 従量課金 | **電気代だけ** |
| 待機中のコスト | ゼロ（使わなければ無料） | **遊ばせると損** |

最後の行が重要。

> **クラウドは「使わないこと」が最適化。ローカルは「使い切ること」が最適化。**

コスト削減という発想をローカルに持ち込むのは、方向が逆。
遊んでいるVRAM・CPU・時間は、節約ではなく**捨てている**のと同じ。

## 1. だから、計算を品質と速度に変換する

賢さで負けるなら、**量で埋め合わせる**。
クラウドでは採算が合わずできないことを、ローカルは無料でできる。

### 1.1 冗長実行（race） — 実装済み

同じ作業を複数モデルに**同時に**投げ、最初に完了したものを採る。

```
依頼: auth.ts のバグを直す
  ├─ qwen3:30b-a3b   → 32秒で完了  ← 採用
  └─ qwen2.5-coder:7b → 打ち切り
```

- 速いモデルが当たれば速く終わる
- 速いモデルが外しても、遅い確実なモデルが拾う
- **単独実行より遅くなることはない**（最速の成功に律速される）
- 片方のモデルが壊れていても全体は完走する

クラウドでこれをやると料金が2倍になる。ローカルはゼロ。
**これがローカル側の一方的な優位。**

```jsonc
{ "id": "fix-auth", "laneId": "coder", "writes": ["auth.ts"],
  "instruction": "...", "raceWith": ["ollama:qwen2.5-coder:7b"] }
```

### 1.2 最良選択（bestOf） — 実装済み

複数の答えを作り、**客観的に採点**して最良を採る。

```
同じ依頼を3回 → それぞれテストを実行 → 通った数が多いものを採用
```

race と違い最後まで待つので遅い。そのぶん品質が上がる。
「テストが通るか」のように機械が採点できる場面で使う。

**賢さの不足を、試行回数で買い戻す手法。**
1回で7割正解のモデルでも、3回試して検証すれば実質的な正答率は上がる。

### 1.3 常時ロード — 実装済み

使うモデルを起動時に温め、載せたまま保持する。
作業開始時のロード待ち（32B級なら1〜3分）がゼロになる。

```
温め中: qwen3-30b-a3b-q4_k_m.gguf...
常駐: qwen3-30b-a3b-q4_k_m.gguf (48.2秒)
常駐: qwen2.5-coder-7b-q4_k_m.gguf (12.1秒)
  — 待ちなしで開始できます
```

**空いているVRAMは節約ではなく損失**なので、既定で使い切る（VRAMの95%まで）。
溢れそうになったら、**使っていないものから**降ろす。

守っている規則:

| 規則 | 理由 |
|---|---|
| 使用中のモデルは降ろさない | 実行中の作業が壊れる |
| 降ろすのは最も長く使われていないもの | 次に使う可能性が最も低い |
| 全部使用中なら降ろさずに載せる | 作業を止めないことを優先する |
| 同じモデルへの同時要求で二重ロードしない | VRAMを二重に食う |

Ollama はモデル保持を自前で行うため、常時ロードは llamacpp のときだけ適用する。
二重に管理すると、こちらが降ろした直後に向こうが載せ直す噛み合いが起きる。

### 1.4 これから実装するもの

| 手法 | 内容 | 効く場面 |
|---|---|---|
| 先読み | 利用者が考えている間に、リポジトリの索引・テスト実行を済ませておく | 依頼した瞬間から本題に入れる |
| 自己検証ループ | 生成→テスト→失敗なら自分で直す、を無人で回す | 品質が時間で買える |
| 投票 | 同じ問いを複数モデルに投げ、答えが割れたら再検討する | 見逃しの削減 |

いずれも**計算を消費して品質を上げる**手法で、クラウドでは高くつく。

## 2. 何を最適化するのか

「効率」という言葉を、節約の意味で使わない。

| 指標 | 扱い |
|---|---|
| ❌ トークン消費量 | **見ない。** ローカルではゼロ円 |
| ❌ VRAM使用量の少なさ | **見ない。** 空きVRAMは無駄 |
| ⭕ 1件を完了させるまでの実時間 | **これが唯一の指標** |
| ⭕ 無人で連続稼働できる時間 | 止まらないことが価値 |
| ⭕ ハードウェアの使用率 | 低いのは損 |

`src/runtime/efficiency.ts` が計算しているのも、
コストではなく**「1件完了までの期待実時間」**である。
そこにやり直し・見逃し・モデル切替のコストを時間として積む。

## 3. 高性能環境ではそのまま伸びる

この設計は、スペックが上がると**設定を変えずに性能が乗る**。

| 環境 | 効き方 |
|---|---|
| VRAM 8GB | 1モデル常駐。冗長実行はレーンを分けて2本まで |
| VRAM 16GB | 2モデル常駐。race が常時使える |
| VRAM 24GB+ | 3モデル以上。bestOf と投票が現実的になる |
| 複数GPU | レーンをGPUごとに割り当て、完全並列 |

**低スペックでも動く**（[段階的劣化](DEGRADATION.md)）ことと、
**高スペックなら伸びる**ことは、同じ設計の裏表。
スペックが決めるのは速度と冗長度であって、動くかどうかではない。

## 4. まとめ

- 賢さで大手に勝てない。**勝てる軸はパフォーマンスだけ**
- ローカルは計算が無料。**遊ばせるのは節約ではなく損失**
- だから **冗長実行・最良選択・常時稼働** でクラウドができないことをやる
- 見る指標は **1件完了までの実時間** のみ。トークン量もVRAM節約も見ない
