# パフォーマンスで戦う

## 0. 前提の再確認

ローカルLLMは、モデルの賢さでは大手クラウドに負ける。
これは当面ひっくり返らない。だからそこで戦っても勝てない。

一方で、ローカルには**クラウドが構造的に持てない資産**がある。

| | クラウド | ローカル |
|---|---|---|
| トークン単価 | かかる | **ゼロ** |
| 利用制限 | ある | **無い** |
| 同時実行 | 課金で青天井だが金がかかる | **ハードの上限まで無料** |
| 常時稼働 | 従量課金 | **電気代だけ** |
| 待機中のコスト | ゼロ（使わなければ無料） | **遊ばせると損** |

最後の行が重要。

> **クラウドは「使わないこと」が最適化。ローカルは「使い切ること」が最適化。**

コスト削減という発想をローカルに持ち込むのは、方向が逆。
遊んでいるVRAM・CPU・時間は、節約ではなく**捨てている**のと同じ。

## 1. だから、計算を品質と速度に変換する

賢さで負けるなら、**量で埋め合わせる**。
クラウドでは採算が合わずできないことを、ローカルは無料でできる。

### 1.1 冗長実行（race） — 実装済み

同じ作業を複数モデルに**同時に**投げ、最初に完了したものを採る。

```
依頼: auth.ts のバグを直す
  ├─ qwen3.6:35b-a3b-coding-nvfp4   → 32秒で完了  ← 採用
  └─ qwen3.5:9b → 打ち切り
```

- 速いモデルが当たれば速く終わる
- 速いモデルが外しても、遅い確実なモデルが拾う
- **単独実行より遅くなることはない**（最速の成功に律速される）
- 片方のモデルが壊れていても全体は完走する

クラウドでこれをやると料金が2倍になる。ローカルはゼロ。
**これがローカル側の一方的な優位。**

```jsonc
{ "id": "fix-auth", "laneId": "coder", "writes": ["auth.ts"],
  "instruction": "...", "raceWith": ["ollama:qwen3.5:9b"] }
```

### 1.2 最良選択（bestOf） — 実装済み

複数の答えを作り、**客観的に採点**して最良を採る。

```
同じ依頼を3回 → それぞれテストを実行 → 通った数が多いものを採用
```

race と違い最後まで待つので遅い。そのぶん品質が上がる。
「テストが通るか」のように機械が採点できる場面で使う。

**賢さの不足を、試行回数で買い戻す手法。**
1回で7割正解のモデルでも、3回試して検証すれば実質的な正答率は上がる。

### 1.3 常時ロード — 実装済み

使うモデルを起動時に温め、載せたまま保持する。
作業開始時のロード待ち（32B級なら1〜3分）がゼロになる。

```
温め中: qwen3-30b-a3b-q4_k_m.gguf...
常駐: qwen3-30b-a3b-q4_k_m.gguf (48.2秒)
常駐: qwen3-8b-q4_k_m.gguf (12.1秒)
  — 待ちなしで開始できます
```

**空いているVRAMは節約ではなく損失**なので、既定で使い切る（VRAMの95%まで）。
溢れそうになったら、**使っていないものから**降ろす。

守っている規則:

| 規則 | 理由 |
|---|---|
| 使用中のモデルは降ろさない | 実行中の作業が壊れる |
| 降ろすのは最も長く使われていないもの | 次に使う可能性が最も低い |
| 全部使用中なら降ろさずに載せる | 作業を止めないことを優先する |
| 同じモデルへの同時要求で二重ロードしない | VRAMを二重に食う |

Ollama はモデル保持を自前で行うため、常時ロードは llamacpp のときだけ適用する。
二重に管理すると、こちらが降ろした直後に向こうが載せ直す噛み合いが起きる。

### 1.4 先読み — 実装済み

利用者が指示を考えている間に、状況把握を済ませておく。

```
起動
  ↓ （裏で並行）ファイル索引 / git状態 / テストコマンドの検出
利用者が指示を入力している間に完了
  ↓
依頼が来た瞬間、作業者は「このプロジェクトはこうなっている」を持って始める
```

先読みが無いと、最初の数ターンが調査で消える。

```
（先読みなし）
  ターン1: list_files で全体を見る
  ターン2: package.json を読んでテストの流し方を調べる
  ターン3: git status を見る
  ターン4: ようやく本題

（先読みあり）
  ターン1: 本題
```

**1トークン1秒のモデルでは、この3ターンが数分の差になる。**

渡す内容:

```
種別: Node.js
git: master（未コミットの変更 1 件）
  src/wip.ts
実行できるコマンド:
  test: npm test
  build: npm run build
ファイル 42 件。直近に更新されたもの:
  src/auth.ts
  ...
この情報は既に取得済みです。同じことを調べ直す必要はありません。
```

守っている規則:

| 規則 | 理由 |
|---|---|
| 起動を待たせない | 先読みは非同期。UIは即座に使える |
| 依頼時にまだ途中なら、最大3秒だけ待つ | 数百ミリ秒待つ方が、モデルが数ターン調べるより遥かに速い |
| 上限を超えたら諦めて進む | 先読みのために作業を止めない |
| 失敗しても本体を止めない | 状況が無くても作業は始められる |
| 書き込み後は裏で作り直す | 古い索引を渡すと誤った判断を招く |

### 1.5 自己検証ループ — 実装済み

書いて終わりにしない。テストを流し、失敗したら自分で直させ、通るまで繰り返す。

```
作業前の状態を確認中: npm test
  作業前から失敗しています
· write_file src/math.mjs
検証 1回目: npm test
✗ 検証に失敗（1回目）
修正させています...
· write_file src/math.mjs
検証 2回目: npm test
✓ 検証を通過しました (0.3s)
```

**これが「時間で品質を買う」の実体。**
1回で7割しか当たらないモデルでも、失敗を読ませて直させれば実質的な到達点は上がる。
クラウドなら往復ごとに課金されるが、ローカルはゼロ。

#### 放置すると壊れる2つの道

無人で回す以上、以下は必ず塞ぐ。

**1. テストを消して「通す」**

「テストを通す」を目標にすると、モデルは最短経路として
テストの削除や skip を選ぶことがある。それは通ったのではなく、確認をやめただけ。

作業の前後でテストの規模を比べ、減っていたら通過とみなさない。

| 検出するもの | 扱い |
|---|---|
| テストファイルの削除 | 通過とみなさず、元に戻させる |
| テスト件数の減少 | 同上 |
| skip の追加 | 件数から差し引いて数える |
| テストの追加 | 問題なし |

**2. 直せない失敗を延々と投げ続ける**

打ち切りを3つ持つ。

| 条件 | 既定 |
|---|---|
| 同じ失敗が3回続いた | 原因が掴めていないと判断して停止 |
| 往復回数の上限 | 5回 |
| ループ全体の時間上限 | 60分 |

#### 作業前の状態を必ず確認する

**元から失敗していたのか、この作業で壊したのかを区別しないと、
直せない失敗をモデルに何度も投げることになる。**

そこで作業前にも1回検証を流し、失敗の内容が同じなら
「この作業が原因ではない」と判定してループに入らない。

```
この失敗は作業前から出ています。今回の作業が原因ではありません。
```

失敗の照合には、実行ごとに変わる値（所要時間、一時パス）を落とした要約を使う。
これが無いと同じ失敗が毎回別物に見えて、進捗判定も効かなくなる。

### 1.6 これから実装するもの

| 手法 | 内容 | 効く場面 |
|---|---|---|
| 投票 | 同じ問いを複数モデルに投げ、答えが割れたら再検討する | 見逃しの削減 |

いずれも**計算を消費して品質を上げる**手法で、クラウドでは高くつく。

## 2. 何を最適化するのか

「効率」という言葉を、節約の意味で使わない。

| 指標 | 扱い |
|---|---|
| ❌ トークン消費量 | **見ない。** ローカルではゼロ円 |
| ❌ VRAM使用量の少なさ | **見ない。** 空きVRAMは無駄 |
| ⭕ 1件を完了させるまでの実時間 | **これが唯一の指標** |
| ⭕ 無人で連続稼働できる時間 | 止まらないことが価値 |
| ⭕ ハードウェアの使用率 | 低いのは損 |

`src/runtime/efficiency.ts` が計算しているのも、
コストではなく**「1件完了までの期待実時間」**である。
そこにやり直し・見逃し・モデル切替のコストを時間として積む。

## 3. 高性能環境ではそのまま伸びる

この設計は、スペックが上がると**設定を変えずに性能が乗る**。

| 環境 | 効き方 |
|---|---|
| VRAM 8GB | 1モデル常駐。冗長実行はレーンを分けて2本まで |
| VRAM 16GB | 2モデル常駐。race が常時使える |
| VRAM 24GB+ | 3モデル以上。bestOf と投票が現実的になる |
| 複数GPU | レーンをGPUごとに割り当て、完全並列 |

**低スペックでも動く**（[段階的劣化](DEGRADATION.md)）ことと、
**高スペックなら伸びる**ことは、同じ設計の裏表。
スペックが決めるのは速度と冗長度であって、動くかどうかではない。

## 4. まとめ

- 賢さで大手に勝てない。**勝てる軸はパフォーマンスだけ**
- ローカルは計算が無料。**遊ばせるのは節約ではなく損失**
- だから **冗長実行・最良選択・常時稼働** でクラウドができないことをやる
- 見る指標は **1件完了までの実時間** のみ。トークン量もVRAM節約も見ない
