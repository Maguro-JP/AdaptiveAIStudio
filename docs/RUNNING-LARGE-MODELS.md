# 32B級を動かすには

## 0. 結論から

RTX 4060 (VRAM 8GB) / RAM 32GB で、32B の Q4_K_M は **動く**。
ただし全部をGPUに載せるのではなく、**層を分割して一部をCPUに置く**。

```
qwen3:32b Q4_K_M
  部分オフロード (GPU 16/64層) / context 8192 / 約 3 tok/s
  VRAM 7.0GB / RAM 13.8GB
  1000トークンの応答: 約 6分
```

「載らない」のではなく「遅い」。この区別が全て。

## 1. なぜ載るのか — メモリの計算

32B を Q4_K_M で量子化すると、重みは約 **19.8GB**。

```
19.8GB = 32.8e9 パラメータ × 4.83 bit ÷ 8
```

VRAM 8GB には入らない。しかし **RAM 32GB には余裕で入る**。
llama.cpp は層単位でGPUとCPUに分けて置けるので、

```
VRAM 8GB のうち使えるのは約 7.1GB（OS・CUDAコンテキストで 0.9GB 消費）
  − KVキャッシュ (context 8192, f16)      2.1GB
  − 推論作業バッファ                       0.4GB
  ────────────────────────────────
  = 4.6GB を重みに使える
    ÷ 1層あたり 0.31GB (19.8GB ÷ 64層)
  = 約 16層をGPUへ

残り 48層 (14.8GB) は RAM へ
```

**このプロジェクトはこの計算をコードで持っている**（`src/runtime/planner.ts`）。
「載るか」を人間が試行錯誤するのではなく、機械が計算して設定を出す。

## 2. なぜ遅いのか — 速度を決めるのは帯域

自己回帰生成は、1トークン出すごとに**全ての活性重みを読み直す**。
つまり速度は計算力ではなく **メモリ帯域** でほぼ決まる。

| 置き場所 | 帯域の目安 | 32Bで1トークン出すのに |
|---|---|---|
| VRAM (GDDR6) | 272 GB/s | 該当分は一瞬 |
| RAM (DDR5) | 70 GB/s | 14.8GB ÷ 70 = 0.21秒 |

CPU側の 14.8GB を読むのに毎トークン約0.2秒。
実効帯域は理論値の6〜7割なので、**約 3 tok/s** になる。

GPU層を増やせば速くなるが、VRAMは既に埋まっている。
だからこの環境で 32B を大幅に速くする方法は無い。**遅いのは物理的な帰結。**

## 3. だが「遅い」を回避する道はある — MoE

Mixture-of-Experts は、総パラメータは大きいが
**1トークンあたりに使うパラメータ（活性パラメータ）が小さい**。
読む量が減るので、CPU側に置いても速い。

同じ環境での比較:

| モデル | 総params | 活性params | 配置 | 速度 | 1000tok |
|---|---|---|---|---|---|
| qwen3:32b | 32.8B | 32.8B | GPU 16/64層 | **3 tok/s** | 約6分 |
| qwen3-coder:30b (MoE) | 30.5B | **3.3B** | GPU 16/48層 | **33 tok/s** | 約31秒 |
| qwen3:14b | 14.8B | 14.8B | GPU 30/48層 | 10 tok/s | 約2分 |
| qwen3:8b | 7.6B | 7.6B | 全層GPU | 41 tok/s | 約25秒 |

**MoEは同規模の通常モデルより10倍以上速い。**
「大きいモデルを低スペックで動かす」目的に対して、現状これが最良の答え。

`llama3.1:70b` も動くが、量子化をQ3_K_Mまで下げ、contextを4096に縮めて
**約1.6 tok/s**（1000トークンに11分）。夜間バッチ用途になる。

## 4. 実装 — 何を作るか

### 4.1 すでに実装した: 実行可能性プランナ

`src/runtime/planner.ts`。モデル諸元とマシン諸元から、実行設定を計算する。

```ts
planExecution({ model, machine, desiredContext: 8192 })
// → { gpuLayers, contextLength, kvCacheType, useMmap, estimatedTps, degradations }
```

劣化は品質を落とさないものから使う。

```
1. GPU層数を減らす      速度だけ落ちる      ← まずこれを使い切る
2. KVキャッシュを量子化  ほぼ落ちない
3. contextを縮める      扱える情報量が減る
4. 量子化を下げる        品質が落ちる        ← 最後の手段
5. mmapでディスク実行    非常に遅いが動く
```

32B は 1 だけで収まるので、**量子化を下げずに済む**（テストで固定してある）。

### 4.2 実装した: llama.cpp 直接制御ランタイム（S1）

プランナの出力を実際に適用するには、Ollama では足りない。
Ollama はオフロード層数を自動で決め、こちらから細かく指定できないため。

`llama-server` を子プロセスとして起動し、プランナの値を渡す。

その `llama-server` は**この道具が自分で用意する**（`npm run llama`）。
以前は PATH にあるものを呼んでいたが、実体は LM Studio などが入れたもので、
**それを消されたら動かなくなる**。他人の同梱物に相乗りする作りはやめた。

用意するときに一度起動して、動くことまで確かめる。
置けたことと動くことは別で、実際に Linux では
共有ライブラリを見つけられずに落ちた（配布物は実行ファイルの隣に
libllama.so を置くが、Linux と macOS はそこを自動では探さない）。
起動時に探し場所を渡している（`src/runtime/llama-env.ts`）。

```
llama-server
  --model qwen3-32b-q4_k_m.gguf
  --n-gpu-layers 16          ← プランナが計算した値
  --ctx-size 8192
  --cache-type-k q8_0
  --parallel 2               ← レーンの並列度
  --port 8081
```

`llama-server` は **OpenAI互換API** を出すので、
既存の `OpenAiCompatibleProvider` がそのまま繋がる。
**Provider層に変更は要らない。** 必要なのはプロセスの起動・監視・停止だけ。

| 部品 | 状態 |
|---|---|
| `LlamaCppRuntime` プロセス起動・ヘルスチェック・停止 | **実装済み** |
| プランナ計算値の引数への反映 | **実装済み**（テストで固定） |
| マシン検出（VRAM/RAM） | **実装済み** |
| ロード/アンロード（VRAM解放） | **実装済み**。プロセス終了を待ってから返る |
| GGUFメタデータからの層数取得 | 未実装。現在はファイル名から推定（S2） |

起動時の待ち方に2つの要件がある。

- **巨大モデルのロードは数分かかる**ので、既定で10分待つ
- **プロセスが死んだ場合は待たずに即座に失敗**させ、標準エラーを添えて返す

「遅い」と「壊れている」を区別しないと、
落ちたプロセスを10分待つことになる。

### 4.3 起動時に何が起きるか

```
1. マシンを測定（初回のみ、以後キャッシュ）
     VRAM 8.0GB / RAM 32GB / 帯域 68GB/s 実測

2. モデルの諸元を取得（GGUFのメタデータから）
     32.8B / 64層 / KVヘッド8 / Q4_K_M

3. プランナが計算
     GPU 16/64層 / context 8192 / KV f16 / 約3 tok/s

4. 利用者へ予告
     「約3 tok/s です。1000トークンの応答に約6分かかります。実行しますか？」

5. llama-server を起動（初回ロードに1〜3分）

6. OpenAI互換APIとして既存のProviderが接続
```

## 5. 並列と直列 — どちらでもよい

並列実行は **売り** であって、必須ではない。

| スタイル | 構成 | 向く環境 |
|---|---|---|
| **並列** | 小モデルを1レーンに載せ、`parallel: 4` で同時実行 | VRAMに余裕がある / 定型作業が多い |
| **直列リレー** | レーンを渡り歩き、1件ずつ順に処理 | VRAMが厳しい / 大モデルを使いたい |
| 混成 | 小モデルのレーンは並列、大モデルのレーンは `parallel: 1` | 現実的にはこれ |

**32B を使うなら直列リレーになる。** VRAMが埋まるので並列にできない。
それでも「PMが32Bで分解 → 作業者が7Bで並列実装 → 検査を32Bで」のように、
職能ごとにモデルを変えるリレーは成立する。

スケジューラは直列を劣化ではなく正規の実行スタイルとして扱う。

- 全レーン `parallel: 1` でも全タスクが完了する（テスト済み）
- **今ロードされているモデルのタスクを優先し、モデル切替の回数を最小化する**（テスト済み）

切替コスト（アンロード→ロード）は数秒〜数分かかるため、
この最小化が直列スタイルの実効速度をそのまま決める。

```jsonc
// 直列リレー: 1件ずつ、モデルを渡り歩く
{ "agent": {
  "maxTotalParallel": 1,
  "lanes": [
    { "id": "big",   "candidates": ["local:qwen3:32b"], "parallel": 1 },
    { "id": "small", "candidates": ["local:qwen3:8b"],  "parallel": 1 }
  ]
} }

// 並列: 1つのモデルを複数の作業者で共有
{ "agent": {
  "lanes": [{ "id": "coder", "candidates": ["local:qwen3:8b"], "parallel": 4 }]
} }
```

高性能環境ではレーンごとの `parallel` を上げるだけで、そのまま性能が乗る。
**設定を書き直す必要はない。スペックが上限を決めるのは速度であって、可否ではない。**
