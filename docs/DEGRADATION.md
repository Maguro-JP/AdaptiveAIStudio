# 遅くても動く — 段階的劣化の設計

## 0. 原則

> **「動かせません」と言わない。遅くしてでも動かす。**

LM Studio や Ollama は「VRAMに載らない」と判断すると起動を拒否する、
あるいはOOMで落ちる。これは短時間で結果が欲しいツールとしては正しいが、
**開発を止めないことが目的の基盤としては誤り**である。

速度は環境のスペックに依存してよい。
依存してはいけないのは「動くかどうか」の方。

## 1. なぜ「載らない」モデルが動くのか

VRAMに全部載せる必要はない。実際には4段の記憶階層がある。

| 段 | 置き場所 | 速度の目安 | 手段 |
|---|---|---|---|
| 1 | VRAM | 30〜60 tok/s | 全層GPU |
| 2 | VRAM + RAM | 3〜15 tok/s | **部分オフロード**(`n_gpu_layers`) |
| 3 | RAM のみ | 1〜5 tok/s | CPU推論 |
| 4 | ディスク | 0.1〜1 tok/s | **mmap**（ページキャッシュ経由） |

llama.cpp は 2〜4 をすべて扱える。
つまり RTX 4060 / RAM 32GB でも、
**32B や 70B の量子化モデルは「遅いが動く」**。

LM Studio が拒否するのは、この遅さを許容しない設計だから。
本プロジェクトは許容する。

## 2. 実行可能性プランナ（Feasibility Planner）

モデルを選んだとき、「載るか/載らないか」の二値判定をしない。
**必ず1つの実行可能な設定を返す**コンポーネントを置く。

```
入力: モデル(サイズ・層数・量子化), マシン(VRAM/RAM/ディスク空き)
出力: 実行プラン { gpuLayers, contextLength, kvCacheType, mmap, 予測速度 }
```

### 劣化の順序

上から順に試し、最初に収まった設定を採用する。
**この順序が品質の劣化を最小にする。**

```
1. 全層GPU + 目標コンテキスト長
        ↓ 載らない
2. GPU層数を減らす（部分オフロード）        ← 速度が落ちる。品質は落ちない
        ↓ まだ載らない
3. KVキャッシュを量子化 (q8_0 → q4_0)       ← 長文でわずかに劣化
        ↓ まだ載らない
4. コンテキスト長を縮める                    ← 扱える情報量が減る
        ↓ まだ載らない
5. 量子化を下げる (Q4_K_M → Q3_K_M → IQ2)   ← 品質が落ちる。最後の手段
        ↓ まだ載らない
6. mmap でディスクから実行                   ← 非常に遅いが動く
```

**重要:** 2〜4 は品質をほとんど落とさず「遅くなるだけ」。
だから先に使い切る。量子化を下げるのは最後にする。

### 出力例

```
qwen2.5-coder:32b-q4_K_M を選択

  プラン: 部分オフロード
    GPU層数     : 27 / 65
    コンテキスト: 8192
    KVキャッシュ: q8_0
    予測速度    : 約 4 tok/s（1000トークンの応答に約4分）

  この設定で実行しますか？ [Y/n]
```

**予測速度と待ち時間を必ず先に見せる。** 遅いこと自体は問題ないが、
どれくらい遅いか分からないまま待たされるのは問題。

## 3. 「停滞」で打ち切る（実装済み）

総実行時間でタイムアウトを掛けると、低速環境では正常な生成が殺される。
1 tok/s で 2000トークン生成すれば33分かかるが、これは異常ではない。

そこで打ち切り条件を **「トークンが一定時間まったく来ないこと」** に変えた。

| 条件 | 既定値 | 意味 |
|---|---|---|
| 最初の1トークンまで | 10分 | 巨大モデルのロード・ディスク読み出しを待つ |
| トークン間の停滞 | 2分 | 進んでいないと判断して打ち切る |

**生成が1トークンでも進んでいる限り、何時間でも待つ。**
これが「遅くてもいいから動く」の実装上の核心。

## 4. 運用スタイルは選べる

「大きいモデル1つ」と「小さいモデル複数」は、
どちらが正しいかではなく **編成の好み**。両方を成立させる。

### スタイルA: 少数精鋭（大モデル1つで全職能を兼任）

```jsonc
{
  "style": "solo",
  "staff": { "*": ["local:qwen2.5-coder:32b"] }
}
```

- 全職能を1モデルが兼任。モデル切替が発生しない
- 部分オフロードで動くので遅い（数 tok/s）
- **判断の質が高く、一貫性がある**
- 夜間に回す・じっくり考えさせる用途に向く

### スタイルB: 大量採用（小モデル多数を並列）

```jsonc
{
  "style": "swarm",
  "staff": {
    "control": ["local:qwen2.5:14b"],
    "impl.worker": ["local:qwen2.5-coder:7b"],
    "qa.reviewer": ["local:qwen2.5-coder:7b"]
  },
  "lanes": { "coder7b": { "parallel": 4 } }
}
```

- 同一モデルを複数の作業者が共有して並列実行
- 1件あたりは速いが、難しい判断は苦手
- 定型作業を大量にさばく用途に向く

### スタイルC: 混成（既定）

- 統制・PM = 大モデル or クラウド（遅くても質が要る）
- 作業者 = 小モデルを並列（数をこなす）

### スタイルD: MoEモデル

Mixture-of-Experts（総パラメータは大きいが、
1トークンあたりの活性パラメータが小さい）は、この環境と相性が良い。

- 総サイズが大きいのでVRAMには載りきらない → RAMへオフロード
- **活性パラメータが小さいのでCPU推論でも比較的速い**
- 「大きいモデルを遅く動かす」の中では最も費用対効果が高い

## 5. 起動時のマシン測定

初回起動時に一度だけ実測し、以後の判断に使う。

```
検出: VRAM 8GB / RAM 32GB / ディスク空き 400GB
実測: メモリ帯域 ... GB/s
      → 7B-Q4 全層GPU     : 約 45 tok/s
      → 14B-Q4 部分(38層) : 約 11 tok/s
      → 32B-Q4 部分(27層) : 約  4 tok/s
      → 70B-Q4 ディスク   : 約 0.4 tok/s（1件あたり数十分）
```

理論値ではなく**自分のPCでの実測値**を持つ。
これがプランナの精度と、ユーザーへの待ち時間予告の根拠になる。
`model_catalog.measured_tps` に蓄積する。

## 6. ローカルランタイムの選択

| 用途 | 実装 | 理由 |
|---|---|---|
| 通常運用 | Ollama | Windowsでの導入・モデル管理が容易 |
| **限界を攻める** | **llama.cpp 直** | `n_gpu_layers` / KV量子化 / mmap を細かく制御できる |

Ollama は自動でオフロード層数を決めるが、細かい制御ができず、
判断を誤ると起動失敗やOOMになる。
**「載らないモデルを無理やり動かす」用途では llama.cpp を直接叩く。**

両方を `LocalRuntime` インターフェースの裏に置き、
プランナの出力に応じて使い分ける。どちらにも依存しない。

## 7. これがなぜ価値になるか

現状のツールは「速く動くこと」を前提に、動かないものを切り捨てている。
そのため **低スペック環境の利用者は、上位モデルを一切試せない**。

「遅くても動く」を保証すると、こうなる。

- 手持ちのPCで、本来動かないはずのモデルを試せる
- 急ぎの作業は小モデル、重要な判断は大モデルに夜間で回す、という使い分けができる
- PCを買い替えたときは、同じ設定のまま速くなるだけ（設定の作り直しが不要）

**スペックが上限を決めるのは速度であって、可否ではない。**
