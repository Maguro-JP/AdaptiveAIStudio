# ハーネス設計 — モデルに「お願い」しない

## 0. 前提

> 全てAIに任せて問題無ければ良いけど、結局人と同じで誤った選択はする。

これが出発点。**モデルが正しく選ぶことに賭けない。**

プロンプトに「テストを消さないでください」と書くのは要求であって保証ではない。
守らせたいことは、実行の手前で止める。

| 方式 | 実体 | 守られるか |
|---|---|---|
| プロンプトで禁じる | お願い | モデル次第 |
| **ハーネスで止める** | **実行前の拒否** | **必ず** |

これは人の組織でも同じで、
「気をつけてください」より「権限を渡さない」方が確実に事故が減る。

## 1. 仕組み

ツールと規則の間にハーネスが立つ。

```
モデル
  ↓ ツール呼び出し
┌──────────────────────────┐
│ ハーネス                  │
│  規則(pre)  → deny なら実行させず、理由をモデルへ返す │
│  ツール実行                                        │
│  規則(post) → 気づかせる情報を差し込む              │
│  監査ログ                                          │
└──────────────────────────┘
  ↓
ファイル / コマンド
```

**ツールは規則を知らない。規則はツールを知らない。**
繋ぐのはハーネスだけなので、ツールを増やしても規則を書き直さずに済む。

拒否は例外ではなく、モデルが読める文字列で返す。
止めるのが目的ではなく、**考え直させるのが目的**だから。

```
⛔ read-before-write: src/math.mjs をまだ読んでいません。
   write_file は全文を置き換えるため、先に read_file で現在の内容を確認してください。
```

## 2. 組み込み規則

それぞれ「モデルがやりがちな誤った選択」に対応している。

| 規則 | 止めるもの | なぜ |
|---|---|---|
| `workspace-boundary` | 作業ディレクトリの外の読み書き | 範囲外の事故 |
| `protected-paths` | `.env` / lockfile / `.git` / 鍵への書き込み | 善意で始まる事故 |
| `test-protection` | テストの削除・skip 化 | 「通すために確認をやめる」 |
| `dangerous-commands` | `git reset --hard`、再帰削除、`curl \| sh` | 不可逆な操作 |
| `read-before-write` | 既存ファイルを読まずに全文上書き | 知らない内容を消す |
| `no-repeated-writes` | 同一内容の再書き込み | 行き詰まりの兆候 |
| `blast-radius` | 一度の依頼で N 件を超える書き換え | 理解できていない兆候 |
| `requires-deliberation` | 守りの仕掛けへの変更、広がりすぎた書き換え | 独りで決めさせない |

### 実際の挙動

誤った選択を順に試みるモデルを相手にした結果:

```
· write_file .env
  ⛔ protected-paths: .env は保護されています
· write_file test/math.test.mjs
  ⛔ test-protection: テストが 2 件から 1 件に減っています
· run_command git reset --hard HEAD
  ⛔ dangerous-commands: git の破壊的操作は実行できません
· write_file src/math.mjs
  ⛔ read-before-write: まだ読んでいません
· read_file src/math.mjs        ← 誘導された正しい手順
  ✓
· write_file src/math.mjs
  ✓ 更新: src/math.mjs（+1 -1）
検証 1回目: npm test
✓ 検証を通過しました

許可 2 / 拒否 4
```

`.env` は書き換わらず、テストは2件のまま残った。

## 2.5 検問所と協議

規則がツール呼び出しの**手前**で止めるのに対し、こちらは
**出入りする内容そのもの**と、**守りの仕掛け自体への変更**を見る。

### 検問所（`src/harness/gate.ts`）

外への出口を一つに絞る作りはやめた。数を絞っても中身は見ていないので、
遅くなるだけで安全にはならない。**守るのは扉の数ではなく、通る物**。

| 方向 | 何を見るか |
|---|---|
| 持ち込み（inbound） | 指示の上書き / 役割の乗っ取り / 内部情報の要求 → 止める<br>見えない文字 / 道具の呼び出しに見える記述 → 記録して通す |
| 持ち出し（outbound） | 秘密鍵 / APIキー・トークン / 資格情報を含む設定 → 止める<br>手元の絶対パス → 記録して通す |

三つの決めごと。

1. **判定は機械が行う。** 「怪しいものは報告してください」とモデルに頼む形にすると、
   頼まれた側が見落とした時点で素通りする。頼みではなく、関所として置く。
2. **止めたものは渡さない。** 「危ないので気をつけて読んでください」と添えて渡す形は、
   渡した時点で読まれてしまうので採らない。
3. **記録に合言葉は残さない。** 当たった箇所は前後を少しだけ切り出し、長い文字列は伏せる。

完全ではない。当てはめで見つかるものしか見つからないので、
**すり抜けることを前提に**、止めた記録と通した記録の両方を残す。

### 協議（`src/harness/deliberation.ts`）

小さな変更は止めない方がよい。いちいち相談させれば作業は進まないし、
「毎回聞かれるもの」は読まれなくなって、結局は素通りする。
だから止めるのは**重大な変更だけ**にする。

重大とは、間違えたときに自分では気づけなくなるもの。

- **守りの仕掛けそのもの** — `src/harness/**`、`core/harness-setup`、`agent/tools/paths`、`agent/tools/network`。
  ここが緩むと、以後の検査はすべて素通りになる。「テストを消して通す」と同じことを
  規則の側でやられると、誰も気づけない。
- **広範囲の書き換え** — 既定 8 件（`harness.wideChangeFiles`）。

止め方は「禁止」ではなく「先に議題に出せ」。`deliberate` で次を出す。

| 項目 | 内容 |
|---|---|
| `subject` | 何を変えるか |
| `reason` | なぜ必要か |
| `impact` | 何に影響するか |
| `rollback` | 間違いだったとき、どう戻すか |
| `paths` | 対象ファイル |

案・理由・影響・戻し方を言葉にできない変更は、たいてい本人も分かっていない。
出せたなら通す。判断を奪うのではなく、判断を残させるための関所。

- 体裁だけ埋めた記録（各項目 10 文字未満）は受け取らない。
- 協議は `approval: "auto"` でも自動承認しない。人が読まない協議は記録しか残らない。
- 協議は**依頼をまたいで持ち越さない**。前の依頼で通した話を根拠に別の変更を通せてしまうと、記録の意味がなくなる。
- 通るのは**挙げた対象だけ**。ついでに隣のファイルも、は通らない。

## 3. ループエンジニアリングを構造にする

自己検証だけが特別なのではない。

- 設計 → 実装 → レビュー → 設計
- 生成 → 採点 → 再生成
- 修正 → 再現確認 → 修正

どれも同じ形をしている。

```
目標を決める → 試す → 確かめる → 駄目なら情報を渡して再挑戦
```

**毎回書き下ろすと、打ち切り条件と進捗判定を書き忘れる。**
忘れると無人実行が暴走する。だから形を固定した。

```ts
runLoop(
  { name: 'verify', maxRounds: 5, timeBudgetMs: 3600000, stallLimit: 3 },
  check,    // 今どうなっているか
  attempt,  // どう改善するか
  signal,
)
```

新しいループを足すとき、以下が**自動で付いてくる**。

| 安全装置 | 内容 |
|---|---|
| 回数上限 | 何回試したら諦めるか |
| 時間上限 | 全体で何分まで |
| 停滞検出 | 同じ状態が続いたら、上限を待たずに止める |
| 中断 | 利用者がいつでも止められる |
| 到達済みなら何もしない | 1回目は試行せず検査から入る |

停滞検出には**状態の指紋**を使う。
実行ごとに変わる値（所要時間・一時パス）を落とさないと、
同じ失敗が毎回別物に見えて判定が効かなくなる。

自己検証ループはこのエンジンの上に載っている。
持っているのは「何を検査するか」と「何を差し戻すか」だけになった。

## 4. 取り入れた他の手法

| 手法 | 実装 | 効き方 |
|---|---|---|
| **最小権限** | 職能ごとにツールを絞る（作業者のみ書込可） | 権限が無ければ事故は起きない |
| **チェックポイント** | 書き込み前の状態を控え、打ち切り時に巻き戻す | 中途半端な状態を残さない |
| **監査ログ** | 全ツール呼び出しと判定を記録 | ハーネス自身の誤りを追える |
| **影響範囲の制限** | 一度の依頼で触れるファイル数の上限 | 広げすぎを止め、分割へ誘導 |
| **既存状態の把握** | 作業前に検証を1回流す | 既存の失敗を作業のせいにしない |
| **書き込みロック** | 同一ファイルへの並列書き込みを禁じる | 並列実行時の取り合いを防ぐ |
| **段階的承認** | ask / autoEdit / auto | 自律度を選べる |
| **改ざん検出** | 作業前後でテスト規模を比較 | 事後にも二重で確認 |

### まだ入れていないが有効な手法

| 手法 | 内容 |
|---|---|
| 計画の事前提出 | 大きな依頼では、書き込み前に計画の提出を必須にする |
| 投票 | 同じ問いを複数モデルへ投げ、割れたら再検討する |
| 段階的な権限昇格 | 小さな作業で実績を積むまで、広い権限を渡さない |
| 強いモデルへの委譲 | N回失敗したら、より賢いモデルへ引き継ぐ |
| 受入条件の機械可読化 | 「完了」を人の判断ではなく検査で定義する |

## 4.5 ハーネス自身を測る

**ハーネスが全てを決めるなら、ハーネスにこそフィードバックループが要る。**

規則は増やすほど良いのではない。締めすぎたハーネスはモデルの能力を殺し、
その状態は外から見ると「モデルが馬鹿」に見えるので、原因を取り違える。

良い規則と悪い規則は、**拒否の後に何が起きたか**で見分けられる。

| 拒否の後 | 判定 |
|---|---|
| モデルが正しい手順に移り、作業が完了した | 良好（誘導できている） |
| そのまま作業が失敗した | 過剰の疑い（邪魔をしている） |
| 一度も発動しない | 未発動（削る候補） |

`/harness` で見られる。

```
依頼 12 件 / 拒否なしで完了 58%

規則                   拒否  回復  放棄  回復率  判定
read-before-write         4     4     0    100%  良好
blast-radius              3     0     3      0%  過剰の疑い
protected-paths           0     0     0      0%  未発動

調整の提案:
  blast-radius: 回復率 0% — 緩めるか、拒否文言に次の手順を書き足してください。
```

判断には最低3件の実績を要求する。1件で決めつけない。
拒否が依頼の6割を超えたら、ハーネス全体を疑うよう促す。

## 5. 規則を足すには

```ts
export const myRule: Rule = {
  name: 'my-rule',
  description: '何のための規則かを一行で',
  pre(call, ctx) {
    if (call.name !== 'write_file') return allow;
    return 条件 ? deny('なぜ駄目か、どうすればよいか') : allow;
  },
};
```

拒否の文言には**次にどうすればよいかを必ず書く**。
「駄目です」だけではモデルは同じことを繰り返す。

規則は `src/harness/builtin-rules.ts` に置き、
`buildHarness` で組み合わせる。設定で有効・無効を切り替えられる。

```jsonc
{ "harness": {
  "protectedPaths": ["config/production.*"],
  "maxFilesPerTask": 5,
  "readBeforeWrite": true,
  "rollbackOnGiveUp": false,
  "auditLog": ".aas/audit.jsonl"
} }
```

## 6. 原則

1. **守らせたいことは、実行させないことで守る**
2. **拒否には次の手順を添える**。止めるのではなく誘導する
3. **ループには必ず打ち切り条件を付ける**。エンジンが強制する
4. **ハーネス自身も誤る**。だから監査ログを残す
5. **規則は設定で外せる**。外した結果も記録に残る
