# 判断待ち

long-dev が止まる条件（設計の分岐・人の判断が要る・範囲の外）に当たった件を、1件ずつ置く。
その件だけを脇に置いて、開発は別の作業で続けている。日報がこの一覧を載せるので、答えは
日報への返事か、ここへの書き込みでよい。答えが入ったら、次の周で取り込む。

書き方: 何を決めてほしいか／選択肢／推す案／決まるまで止まっているもの。答えが入ったら「答え」に書き、
取り込んだら「取り込み済み」と印を付けて残す（消さない）。

---

## 1. 行ごとの「戻す」の粒度（2026-09-19 から）

何を決めてほしいか: 差分の `−` の行（消された行）で「戻す」を押したとき、何を戻すか。
いまは、消された行は戻るが、同じ塊で足された行は残る（`test/hunks.test.ts` がこの意味を留めている）。

選択肢:
- A. いまのまま。押した行だけを戻す（`−` を押せば消された行が戻り、足された行は残る）
- B. 塊ごと戻す。`−` でも `+` でも、その塊（消した行と足した行の組）を丸ごと前の姿へ
- C. 両方を置く。行の「戻す」と、塊の「戻す」を別の押し場所にする

推す案: B。消した行と足した行は多くの場合「書き換え」の組で、片方だけ戻すと両方が並んだ変な姿になる。
一行だけ戻したい場面は、エディタで直す方が早い。

決まるまで止まっているもの: 行ごとの「戻す」の見た目と意味の変更（`src/agent/hunks.ts`、画面の差分パネル）。

答え: B（2026-09-26）。塊ごと戻す。— 取り込み済み（09-26、DECISIONS「差分の行を押したら、その書き換えの組を丸ごと戻す」）

## 2. 画面の本体を会話ごとに分けるか（2026-09-12 から）

何を決めてほしいか: 画面で二つの会話を同時に動かせるようにするか。モデルの口は会話ごとに並列だが、
画面の本体（`src/ui/server.ts`）は `Session` を一つしか持たず、二人目の送信は順番待ちに積む。

選択肢:
- A. いまのまま。会話は一つずつ（順番待ち）
- B. `Session` を「共有の作業場」（runtime の口・記憶・harness・MCP・役職・先読み）と「会話ごとの状態」
  （履歴・実行中・依頼文・協議・「戻す」の範囲）に割り、画面は共有を一つ持って、会話ごとの走者を
  `runtime.parallel` 本まで同時に動かす（`docs/DECISIONS.md` 2026-09-12 の「勧める形」）
- C. 会話ごとに `Session` を丸ごと作る。MCP の子と記憶が本数ぶん増え、16GB では載らない

推す案: B。ただし土台の選択で、記憶の保存が重なると利用者のデータが壊れうる種類の変更。
先に「差し替えの provider で二会話を並行させ、履歴と記憶が混ざらないことを見る試験」を作ってから割る。

決まるまで止まっているもの: 画面での複数会話の同時実行。

答え: B（2026-09-26）。会話ごとに分ける。記憶の保存が重なる試験を先に書く。— 取り込み済み（第 1 段と第 2 段の 2a〜2e。DECISIONS「画面の本体を会話ごとに分ける」）

## 3. 段取りが宣言しない書き込み先を、断るところまで強めるか（2026-09-23 から）

何を決めてほしいか: 段取り（`plan()`）で並列に動く担当が、分解のときに宣言しなかったファイルへ
書いたとき、書く手前で断るところまで強めるか。

いまの形（09-25 に読み直して分かった）: 書き込みは止めないが、検収（`src/agent/acceptance.ts` の `accept`）が
「計画に無いファイルが変わっています（N件）」と挙げ、結末を人の判断待ち（needsHuman）にする。
変わったファイルは、この場所の書くツールの分と、作業の前後の git の差（`run_command` の分も入る）から数える。
書き込む道の側は一人ずつ通すので、同時に書いて混ざることは無い。「戻す」は全部載る（09-25）。

選択肢:
- A. いまのまま（検収で挙げ、人の判断待ちにする）
- B. 宣言していない所への書き込みを、その担当の中で断る（harness の規則にする）

推す案: A。分解の宣言はモデルの見込みで外れやすく、断ると正当な直しまで止まる。何が起きたかは検収で見え、
「戻す」で戻せる。

決まるまで止まっているもの: なし（いまの形のまま動いている）。

答え: A（2026-09-26）。いまのまま（検収で挙げる）。— 取り込み済み（変更なし）

## 4. 段取りにも、確かめて落ちたときの自動の巻き戻しを入れるか（2026-09-26 から）

何を決めてほしいか: 段取り（`plan()`）で、終わりの確かめ（テスト）が落ちたときや止めたときに、
作業場を依頼の前の姿へ自動で戻すか。

いまの形（09-26 に読み直して分かった）: 送り口（`send()`）は、確かめて落ちたとき（`rollbackOnGiveUp`）に
この場所の書くツールの分も外のツールの分も自動で巻き戻す。段取りには、書くツールの分も含めて
自動の巻き戻しが元から無い。検収が結果を挙げ、全部の変更が「戻す」に載る（外のツールの分は 09-25 から）。
人が見てから、自分で戻す形。

選択肢:
- A. いまのまま（検収で挙げ、戻すかは人が決める）
- B. 送り口と同じく、確かめて落ちたら自動で全部戻す
- C. 自動では戻さず、検収の結果に「戻す」の押し場所を並べて出す

推す案: A。段取りは並列の担当の仕事をまとめて確かめるので、落ちた原因が一人の担当の分でも、
自動で戻すと他の担当の正しい仕事まで消える。検収が結果を見せ、「戻す」は一度で依頼の前の姿へ戻せる。

決まるまで止まっているもの: なし（いまの形のまま動いている）。

答え: B（2026-09-26）。確かめて落ちたら自動で全部戻す。— 取り込み済み（09-26、DECISIONS「段取りでも、確かめて落ちたら全部戻す」）
