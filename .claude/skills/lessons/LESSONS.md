# 失敗の記録

起きたことだけを書く。一般論は書かない。
1件は4行。場面は「次から」を差し込むときの索引になるので、短い名詞で書く。
新しいものを上に足す。

## 2026-09-25 作業場にしか無いファイルを読む試験を、二日続けて bundle で落とした
場面: テスト、bundle
起きたこと: 09-24 は `test/hooks.test.ts` が `.githooks/pre-push` を、09-25 は `test/docs-only-push.test.ts` が `.github/workflows/ci.yml` を読み、どちらも bundle の中で `ENOENT` で落ちた。どちらも `check:bundle` で見つけた
判定の誤り: 手元の `npm test` が通ったことを、配る形でも通る根拠にした。bundle に何が入らないかを書く前に見なかった
次から: `.github` や `.githooks` を開く試験には `sourceOnly`（`inBundle`）を付ける。付け忘れは `test/source-only.test.ts` が落とす

## 2026-09-25 long-dev に auto-dev の止まる条件をそのまま継がせた
場面: long-dev、スキル
起きたこと: AdaptiveAIStudio の long-dev が PR のマージ可否など3つを利用者に聞いて止まり、翌日の Routine まで何もしなかった。Routine 用に E=23h を毎回書かせてもいた
判定の誤り: 期限のある auto-dev の「当たったら止まる」を、終わりの無い long-dev にそのまま使った
次から: long-dev は条件に当たった件だけを脇に置き、判断待ちに書いて次の作業へ進む。期限は付けない。止まるのは利用者が止めろと言ったときだけ

## 2026-09-26 同じ形でもう一度、落ちた wording の試験のままコミットした
場面: コミット、テスト、フック
起きたこと: `node --test ... | grep ...; git diff > x; git add -A && git commit` の形で、wording の上限超えを出力に出したままコミットした。前日に書いた「次から」を読んでいたが、命令をつなぐ形が変わっただけで同じことをした
判定の誤り: 決まりを文章で持っていれば守れると思っていた。命令の形が少し違うと、決まりに当てはめて読まない
次から: コミットの手前で `.githooks/pre-commit` が wording と decisions の試験を回して止める。文章の決まりに頼らない

## 2026-09-25 テストの出力を grep に通してから && でコミットし、落ちたまま入れた
場面: コミット、テスト
起きたこと: `node --test ... | grep ...; git add -A && git commit` の形で、wording のテストが落ちているのにコミットした。出力に fail 1 が出ていたが、後から読んで気づいた
判定の誤り: 前段の終了コードを grep が握りつぶし、&& は grep の成功を見ていた
次から: コミットの前のテストは grep に通さずに終了コードで止める（`node --test ... >log || exit`）。出力を絞るのはその後

## 2026-09-24 わざとバグを入れた後の戻しに `git checkout` を使い、直しごと消した
場面: テスト、わざとバグを入れる
起きたこと: 4 つ目の break test で `git checkout -- checkpoint.ts` で戻したところ、コミット前の直し（restoreAll）が丸ごと消えた。直後の grep で 0 件と出て気づいた
判定の誤り: 「戻す」を git の元に戻すと読んだ。戻したい先は直した後の版で、git には無い
次から: わざとバグを入れる前に直した版を別の場所へ写し、戻すのはその写しから。戻した後に直しが在ることを grep で見る（CLAUDE.md の作り方どおり）

## 2026-09-24 `??` を「前は無い」、文字列を「中身」と決めつけた
場面: 設計、git
起きたこと: untracked なら新しく作られたと読み、utf8 で読んだ文字列をそのまま戻す形にした。`git rm --cached` の後は在るファイルが `??` になり、二進は U+FFFD に化けて戻った
判定の誤り: git の状態と「前が在ったか」を同じものと見た。文字列で持てないものが在ることを考えなかった
次から: 「前」は HEAD で決める。戻すときに元のバイト列に戻らないものは、持たずに「戻せなかった」と言う

## 2026-09-24 フックが入っている前提で押した
場面: push、フック
起きたこと: fresh clone に `core.hooksPath` が無く、`.githooks/pre-push` の確かめが走らないまま push が通った。push のログが 4 行しか無いことで気づいた
判定の誤り: 「pre-push が止める」を、入っているかを見ずに信じた。README の「一度だけ打つ」は打たれない
次から: 押す前に `git config core.hooksPath` を見る。仕組みは `npm install` の `prepare` が入れ、無ければ `test/hooks.test.ts` が落とす

## 2026-09-24 索引を「前」と読み、取れないものを「無い」と読んだ
場面: 設計、レビュー
起きたこと: 外のツールが変えたファイルの前の中身を索引から引いた。`run_command` が `git add` すれば索引は後の中身になる。取れないものを「前は無い」にして、戻すときに在ったファイルを消す形にもしていた。押す前に別の担当に読ませて 21 件見つかり、自分で見つけていたのは 6 件だった
判定の誤り: 「きれいなら索引＝HEAD」を、ツールが索引を動かせることを忘れて使った。取れない失敗を、既定（無い）に倒した
次から: 「前」は、そのターンの中でツールが動かせないものから引く。取れない失敗は「取れなかった」と別に持つ。自分で書いたものは、押す前に別の担当に読ませる

## 2026-09-24 枠切れで赤い CI を理由に、マージを利用者に訊いた
場面: マージ、CI
起きたこと: #28 を枠切れ（4 秒・手順なし・ログ 404）で止めて自分ではマージせず、#31 でも同じ落ち方で止まり、マージしてよいかを訊いた。手元の `npm run check` と `check:bundle` は通っていた
判定の誤り: 「赤なら止まる」を、枠切れと分かっていて手元で確かめた後にも当てはめた。同じ判断を二度させた
次から: CI が枠切れの落ち方で、手元の `npm run check` と `npm run check:bundle` が通っていれば、訊かずに squash でマージする

## 2026-09-24 直せる設計の判断を、選択肢を並べて利用者に投げた
場面: 設計、報告
起きたこと: 巻き戻しの損と、繰り返し出る警告について、3 つの選択肢を並べて「決めてほしい」と報告した。どちらも既定を決めて進められるものだった

次から: 直せる決定は既定を 1 つ決めて進み、決めたことと選ばなかった案を DECISIONS.md に書く。選択肢の一覧を報告に出さない

## 2026-09-24 同じ警告を、了解の口も無く毎回出す設計にした
