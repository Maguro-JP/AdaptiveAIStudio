# 長期開発

終わりの無い開発を、止まらずに回す。判断の土台は `references/principles.md`。
作業量ではなくプロダクトが良くなることが目的で、「変更不要」は失敗ではない。
先に principles.md を読む。周期はその上で回す。

| 周期 | 役目 | 起きる時刻（既定） |
|---|---|---|
| daily | 前日を確かめ、今日やることを決め、次の朝まで auto-dev で働き続ける | 毎日 09:00 JST |
| weekly | 1週間を評価し、来週の計画と価値改善を1つ決める。PR を整理する | 月曜 09:00 JST |
| monthly | 前月を総括し、今月の目標を週単位に分解する | 1日 09:00 JST |

## 初回

そのリポジトリで初めて使うとき、Routine の一覧に `long-dev` が無ければ、作業の前に1行だけ聞く。

```
long-dev の定期実行がまだありません。daily（毎日 09:00 JST に起きて次の朝まで回す）、
weekly（月曜）、monthly（1日）の3つを作りますか。
```

はいなら `scheduler` で3つ作る。いいえなら作らず、以後は聞かない。
黙って作らないのは、daily が毎日1セッションを1日中使うため。それがこの設計の前提で、
減らしたいときは相手が決める。毎回言わなくて済むように、最初に一度だけ聞く。

## 引数

`long-dev daily` `long-dev weekly` `long-dev monthly`。
無ければ、今日が1日なら monthly、月曜なら weekly、それ以外は daily。

## 共通の約束

- 調査は必要なファイルだけ。前回の報告と `docs/knowledge/` を先に読み、同じ調査を繰り返さない
- 検証は手元で。GitHub Actions は PR を作るときだけ動く形にする
- PR は日次か週次の区切りで作る。緊急の小さな修正はその場でよい
- マージは `solo-pr-flow` の判定に従う。テストが通り、範囲が明確で、既存を壊していないなら入れる
- 不要なブランチと PR を残さない
- 分かったことは `docs/knowledge/` にその日のうちに書く
- 報告は `docs/reports/` に残す。`daily/YYYY-MM-DD.md` `weekly/YYYY-Www.md` `monthly/YYYY-MM.md`

## daily

1. 前日の変更を見る。コミット、push、PR、マージ、直したバグ、足したテスト、書いたドキュメント
2. プロジェクトを見直す。新しいバグ、未解決の問題、AI 精度、UX、UI、性能、セキュリティ、技術的負債、テスト、将来のリスク
3. 今日の優先を決める。最も価値の高いものから順に
4. `auto-dev` を `L=auto E=23h` で回す。優先指示に 3 を渡す。次の朝の daily が起きるまで、調査 → 判断 → 実装 → 検証 → 記録を繰り返す。改善対象が無くなったら auto-dev の S2 で止まり、それも「変更不要」として報告に残る
5. 知識は周ごとに書く。まとめて最後に書かない
6. 報告は次の朝の daily が、前日分として書く

報告の形。

```
# YYYY-MM-DD
やったこと: 
良くなったこと: 
AI 精度: 前後の数字。測っていなければ「測っていない」
直したバグ: 
テスト: 出力の要点
知識: docs/knowledge/ に足した項目
GitHub: PR 番号、マージの有無
Actions: 走った回数
残り: 
次に優先するもの: 
```

変更不要だった日は、見た観点と理由を1行で書く。それも報告。

## weekly

1. 今週を評価する。実装した機能、直したバグ、AI 精度、UX、性能、セキュリティ、テスト、技術的負債、知識、GitHub、Actions の使用量
2. 未解決の問題を洗い出し、Critical / High / Medium / Low に分ける
3. 来週の計画を決める。最低1つ、利用者に価値のある新機能か、はっきりした価値改善を入れる。無理な機能追加はしない。既存の改善や精度向上の方が価値が高いならそちら
4. PR を整理する。検証済みで問題なければマージ。不要なブランチと PR を消す
5. Actions の使用量を見て、無駄が無かったか確かめる

報告の形。

```
# YYYY-Www
成果: 
改善: 
AI 精度: 
得た知識: 
解決した問題: 
未解決（Critical/High/Medium/Low）: 
GitHub: 
Actions: 
来週の目標: 
来週のタスク: 
新機能または価値改善: 
リスク: 
```

## monthly

1. 前月を評価する。新機能、バグ、AI 精度、UX、UI、性能、セキュリティ、安定性、テスト、コード品質、技術的負債、利用者の価値、知識、GitHub、Actions
2. プロダクト全体を見直す。強み、弱み、ボトルネック、精度の問題、UX の問題、技術的な問題、将来のリスク
3. 今月の目標を決める。利用者の価値、品質、精度、安定性、性能、セキュリティ、保守性から総合で
4. 週ごとに分解する。各週に目標、タスク、新機能、精度改善、技術改善、テスト、完了条件
5. 優先順位を付ける。重要度、影響、効果、コスト、リスク
6. トークン、Actions、時間を無駄にしない計画にする。品質に要るコストは削らない
7. 今月重点的に蓄える知識を決める

報告の形。

```
# YYYY-MM
前月の成果: 
前月の問題: 
品質の評価: 
AI 精度: 
技術的負債: 
得た知識: 
今月の目標: 
週ごとの計画: 第1週 / 第2週 / 第3週 / 第4週
新機能: 
精度改善の計画: 
技術改善の計画: 
リスク: 
完了条件: 
```

## 定期実行

`scheduler` で3つ作る。daily 毎日 09:00 JST、weekly 月曜、monthly 1日。
1日が月曜なら monthly だけ動かす。monthly が weekly を含む。
daily は次の朝まで回るので、weekly と monthly は daily と同じ時刻に起きて先に評価を済ませ、
そのあと daily の作業に入る。

## やらないこと

- 報告のために変更を作ること。変更不要の日は変更不要と書く
- 前日の報告を読まずに同じ調査をやり直すこと
- Actions を PR 以外で走らせること
- 週次で無理に新機能を入れること。価値の順で選ぶ
- 「今日はやることが無い」で朝のうちに止まること。auto-dev の S2 が3周続くまでは探す

## 他のスキルとの関係

- 周ごとの作業: `auto-dev`。原則は `references/principles.md`
- 定期実行の設定: `scheduler`
- PR のマージと後片付け: `solo-pr-flow`
- CI が落ちたとき: `ci-triage`
- 失敗の記録: `lessons`。自分の判定の誤りはここ、プロダクトの問題は `docs/knowledge/problems.md`
